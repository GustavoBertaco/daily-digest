## AWS What's New

**[Launching External Web Access for Web Search on Amazon Bedrock](https://aws.amazon.com/about-aws/whats-new/2026/08/amazon-bedrock-web-access-web-search/)**
Amazon Bedrock's built-in Web Search tool now supports an `external_web_access` parameter that allows models to retrieve content directly from the public internet, grounding responses in current information beyond the secured AWS environment. Previously Web Search kept all data within AWS with zero external egress; the new parameter lifts that constraint for teams that require live public web access.

**[Web Search in Amazon Bedrock AgentCore adds domain and published date filtering, expands to Europe and Asia Pacific](https://aws.amazon.com/about-aws/whats-new/2026/08/web-search-amazon-bedrock/)**
Web Search in Bedrock AgentCore now supports per-request domain filtering and published-date filtering, giving agents runtime control over which sources and time windows they query without requiring configuration changes between calls. The capability also expands availability to Europe and Asia Pacific regions.

**[Amazon CloudWatch log Centralization now supports log group tag propagation](https://aws.amazon.com/about-aws/whats-new/2026/08/amazon-cloudwatch-centralization-tag-propogation/)**
CloudWatch Centralization, which aggregates log data from multiple accounts and regions into a single destination account, now copies log group tags from source accounts to the destination log groups it creates. Cost, ownership, and compliance tags applied at the source automatically propagate to the centralized log groups and stay in sync.

**[Amazon SageMaker notebooks now support trusted identity propagation](https://aws.amazon.com/about-aws/whats-new/2026/08/amazon-sagemaker/)**
SageMaker Notebooks now support Trusted Identity Propagation (TIP) with Amazon Athena, Amazon Redshift, and Amazon EMR Serverless, enabling per-user access control rather than a shared broad execution role. When connected to a TIP-enabled compute in a TIP-enabled Project, each user's IAM Identity Center identity flows through to AWS Lake Formation, enforcing their individual data permissions at the table, column, and row level.

**[Amazon CloudWatch pipelines adds GeoIP, RDS, and XML processors](https://aws.amazon.com/about-aws/whats-new/2026/08/cloudwatch-geoip-rds-xml/)**
CloudWatch pipelines adds three new processors: an Amazon RDS log parser for native Aurora engine output, an XML parser for structured application logs, and a GeoIP enrichment processor that annotates log events with location data at ingestion time. The additions reduce the need to reprocess raw log data before it can be queried.

**[AWS Cost Anomaly Detection supports third-party models on Amazon Bedrock](https://aws.amazon.com/about-aws/whats-new/2026/08/aws-cost-anomaly-detection-bedrock-3P/)**
AWS Cost Anomaly Detection now monitors spend on third-party foundation models running on Amazon Bedrock — including Anthropic Claude and other provider-hosted models — extending its ML-based anomaly alerting to cover generative AI workloads. Teams running production AI on Bedrock get automatic spend anomaly detection alongside the rest of their AWS costs.

**[Amazon OpenSearch Ingestion is now available in GovCloud Regions](https://aws.amazon.com/about-aws/whats-new/2026/08/opensearch-ingestion-available-govcloud-regions)**
Amazon OpenSearch Ingestion — a fully managed, no-code data ingestion tier for OpenSearch managed clusters and serverless collections — is now available in AWS GovCloud (US-East) and AWS GovCloud (US-West). Government-sector customers can now use its filter, transform, redact, and route capabilities in those regions.

**[AWS Marketplace launches support for Amazon Lightsail](https://aws.amazon.com/about-aws/whats-new/2026/08/aws-marketplace-launch-ami-amazon-lightsail)**
AWS Marketplace now supports launching select AMIs on Amazon Lightsail, combining Marketplace software with Lightsail's fixed-price bundles that include compute, storage, and data transfer allowance. Customers wanting simple, predictable pricing can deploy eligible Marketplace AMIs on Lightsail in just a few clicks.

**[AWS announces a new Availability Zone in the Europe (London) Region](https://aws.amazon.com/about-aws/whats-new/2026/08/aws-new-availability-zone-europe/)**
AWS has added a fourth Availability Zone to the eu-west-2 (Europe London) region, including next-generation AI and ML capacity such as EC2 Trn3 and P6 accelerated instances alongside general-purpose compute. The additional AZ expands fault isolation options for customers building highly available applications in the region.

## AI Engineer

**[Why Your Enterprise Tech Stack Isn't Ready for AI Agents — Christopher Lovejoy & Saul Howard](https://www.youtube.com/watch?v=mav15aW9lLM)**
Christopher Lovejoy and Saul Howard argue that AI agent projects routinely survive technical pilots only to stall when enterprise compliance requirements surface — and that the most common failure mode is developers conflating an audit trail with a debug log.

- **The compliance wall is structural, not a one-off oversight.** The talk's recurring scenario — a PoC that hits accuracy targets and clears the room, then stops cold when compliance asks for an audit trail — reflects a systematic mismatch between what developers build and what regulated enterprises actually require.
- **Audit trail is not a developer log.** Under the frameworks enterprises actually answer to, an audit trail is a complete record of every action an agent took, every data source it touched, and the authorization context at each step — not a timestamped log of API calls.
- **The pattern repeats across organizations.** Lovejoy and Howard have watched the same compliance conversation stop the same meeting repeatedly, suggesting this is a category-level problem rather than a project-by-project oversight.
- **The implication for agent architecture.** Compliance-grade auditability must be designed in from the beginning; retrofitting it onto an agent that already passed its PoC review is the expensive path.

**[Don't be data poor — Anuj Iravane, Anterior](https://www.youtube.com/watch?v=XAsb7MIAzm8)**
Anuj Iravane of Anterior describes the central paradox of medical AI evaluation: the richest ground-truth data comes from real clinical fax records, but contractual constraints forbid retaining, deriving from, or even holding anonymized copies of that data — leaving evaluation pipelines permanently data-poor relative to the production system's actual inputs.

- **Roughly 70% of medical communication still moves by fax.** The AI data problem is grounded in structural healthcare reality: Anterior receives scanned fax bundles exceeding 300 pages, carrying handwriting, checkboxes, tables, and images across a patient's full clinical trajectory.
- **The data you need is the data you cannot keep.** Anterior's contracts rule out retaining clinical fax content, deriving from it, or holding redacted or anonymized copies — which means eval datasets cannot be built from the data the production system actually processes.
- **"An observation through a fuzzy lens over a lifespan."** Iravane's phrase captures the input's character: fragmented, multi-format, spanning decades, and arriving as a scanned document rather than a structured record.
- **Eval poverty is a compliance artifact, not a technical one.** The inability to accumulate evaluation data is driven by contractual constraints, making it a structurally harder problem to solve than a data engineering challenge.

**[How to build an AI-Native Health Company — Dan Feng, Maven Clinic](https://www.youtube.com/watch?v=WJRdLNhrsLQ)**
Dan Feng of Maven Clinic argues that AI has inverted the economics of software development — implementation is now fast and cheap, making extended requirements debate the primary waste — and that Maven's planning process has been restructured to match.

- **The cost moved from building to arguing.** When implementation takes minutes rather than weeks, spending weeks settling requirements before writing any code is the expensive step — the bottleneck shifted from execution to decision-making.
- **Real planning commitment runs two to four weeks.** A one-year roadmap survives only as directional guidance, with the assumption that models will handle whatever capability gaps exist by the time longer-horizon bets would pay off. Actual committed work runs two to four weeks.
- **Requirements documents shrank to one to two pages designed to be argued with.** The goal shifted from specifying things exhaustively upfront to creating a short artifact that generates fast, productive debate and gets to a decision quickly.
- **The transition is organizationally awkward.** Feng signals that compressing planning cycles and shortening requirements documents creates cultural friction — the shift doesn't happen without resistance.

**[Trading Desks to Clinical Trials: Parallels in Applied Vertical AI — Ayush Bhardwaj, Allos AI](https://www.youtube.com/watch?v=Yphdry8ttAQ)**
Ayush Bhardwaj identifies the wall where vertical AI projects quietly stall: not in building the agent, but in the absence of the domain judgment needed to evaluate whether the agent's output is actually correct — a problem he encountered identically at a hedge fund and at a pharma tech company.

- **The wall is evaluation, not construction.** Bhardwaj could build the agent; what was missing was anyone on the team with the domain instinct to judge whether its outputs — trade theses or drug candidates — were any good.
- **The same pattern appeared in finance and in pharma.** Moving from applied AI at a hedge fund to a pharma tech company expecting a different environment, he found the problem identical, including the stall point — suggesting this is structural to vertical AI, not domain-specific.
- **Domain evaluation instinct takes years to build.** An engineer can glance at generated code and flag it as weak because years of practice built that judgment. No equivalent instinct exists by default for specialized outputs like research hypotheses or clinical assessments.
- **Vertical AI projects don't fail dramatically — they lose momentum.** Bhardwaj's framing is that these projects "quietly" stall, implying the absence of a clear failure event makes the problem harder to diagnose and address.

**[Healthcare's Agent Bytecode: X12 as the Harness for AI Agents — Vasant Kearney, Onlay](https://www.youtube.com/watch?v=UyyOoJmuATU)**
Vasant Kearney of Onlay argues that X12 — the EDI standard underlying US healthcare billing — should serve as the authoritative protocol layer for AI agents operating in payer workflows, because no UI surface (phone system, web portal, or X12 feed) is ground truth, and agents grounded in the protocol layer avoid the contradictions that plague surface-level integrations.

- **No UI surface is ground truth in US healthcare payer systems.** A payer's phone system, web portal, and X12 feed are often built by different teams or different contractors, meaning all three can confirm coverage and all three can be wrong — they can also contradict each other and agree on the same incorrect answer.
- **Claim denials despite confirmed coverage are a known failure mode at scale.** Kearney's opening scenario — patient confirmed covered across all three surfaces, claim denied — is not an edge case; it is a predictable result of layered systems with inconsistent state.
- **X12 as the closest thing to a canonical record.** The talk's argument is that the X12 protocol layer represents a more authoritative data source than any rendered UI, and that AI agents operating against X12 directly inherit that relative reliability.
- **Multi-surface inconsistency is structural, not exceptional.** Because payer systems are assembled in layers by disparate teams over time, disagreement among channels is a foreseeable, recurring condition that AI agent design must account for explicitly.

**[200 Million Patient Interactions Later — Vivek Muppalla, Hippocratic AI](https://www.youtube.com/watch?v=AN65uc645mE)**
Vivek Muppalla of Hippocratic AI describes how reaching 200 million clinical conversations across more than 60 health systems changes the arithmetic of proactive patient outreach — turning a resource that the current system rations by clinical severity into something approaching universal access.

- **Proactive care is currently rationed by scarcity.** Almost no one in Muppalla's audience had ever received a proactive call from their healthcare provider — because too few clinicians and too few hours mean only the sickest patients get reached out to.
- **200 million conversations across 60-plus health systems.** Hippocratic AI's production scale represents one of the largest deployments of clinical AI in operation, and that volume is what makes the economic and access argument credible.
- **The tradeoff they refused.** The snippet describes a familiar choice where models accurate enough for clinical work incur a significant cost — the specific form of that tradeoff and how Hippocratic AI resolved it is cut off in the captured excerpt, but the framing implies they found a way to avoid accepting it.

**[AI is the World's largest Relationship Therapist — Clay Cockrell & Tony Fabrikant, CoupleWork AI](https://www.youtube.com/watch?v=yoONZwV2smc)**
Clay Cockrell and Tony Fabrikant argue that ChatGPT has already become the world's largest de facto relationship therapist by volume — not as an aspiration, but as a description of current usage — and that the question for CoupleWork AI is how to make that massive, unstructured usage actually therapeutic.

- **The scale gap between licensed therapy and AI is stark.** BetterHelp spent roughly a decade assembling ~35,000 licensed clinicians to reach 5 million users; ChatGPT sees ~900 million weekly active users, enough of whom open it after relationship conflicts that Cockrell names it the world's largest relationship therapist.
- **People already use AI for relationship crises at scale.** The behavior is happening at 11pm after fights, without prompting from any product design decision — the usage pattern is emergent, not engineered.
- **The broken loveseat is load-bearing.** Cockrell kept a counseling office loveseat whose springs tip couples toward each other despite their resistance — a physical detail that signals what environmental and relational cues matter in human therapeutic contexts and that AI does not replicate.
- **The CoupleWork AI argument is about structure, not replacement.** Because AI relationship counseling is already happening at scale, the question is not whether to allow it but how to structure it so the interactions are more likely to help than harm.

**[Shipping AI to a Million Patients Without an A/B Test — Jared Joselowitz, Ufonia](https://www.youtube.com/watch?v=McknwOzbmyg)**
Jared Joselowitz describes the evaluation architecture behind Dora, a Ufonia voice agent conducting post-op and pre-op patient calls — where the standard ML improvement loop (A/B testing) is unavailable for ethical and legal reasons, and vendor benchmark scores carry no weight at a post-incident review.

- **Clinical AI cannot use A/B testing.** Randomizing patients into the worse model variant is unethical and often illegal, eliminating the most common ML iteration mechanism from the outset and requiring a fundamentally different approach to continuous improvement.
- **Voice calls are irreversible.** Unlike a web UI change that can be rolled back, a spoken clinical interaction cannot be undone — the evaluation stack must catch problems before production, not after.
- **Vendor benchmark scores are not a defense.** Citing a model's published benchmark at a post-incident review is not a valid response; real-world performance under clinical conditions is the only bar that matters to the teams accountable for patient outcomes.
- **200,000 calls across 20 UK hospitals, contracted for 1 million.** Dora's production scale means Ufonia is operating at a volume where the evaluation methodology is a safety-critical engineering problem, not an academic one.

**[Guardrails First: Engineering Member-Facing Health AI — Rashi Agrawal, Hinge Health](https://www.youtube.com/watch?v=YXEqC05WEI0)**
Rashi Agrawal of Hinge Health opens with documented AI health-advice harm — a sodium bromide poisoning case and a Mount Sinai study finding a consumer health AI under-triaged life-threatening emergencies 50% of the time — to argue that guardrails are not optional features in member-facing health products but a precondition for safe deployment.

- **Concrete harm is already documented.** A healthy 60-year-old man who asked an AI assistant how to cut salt from his diet was hospitalized for three weeks with bromide toxicity at 200 times the safe level after it pointed him at sodium bromide.
- **Independent safety testing found critical failure rates.** A study out of Mount Sinai found a consumer health AI under-triaged life-threatening emergencies half the time — a failure rate that would be clinically unacceptable in any formal triage context.
- **ECRI named chatbot misuse the top health technology hazard.** Agrawal situates her argument within a broader risk landscape where a prominent patient safety organization has already flagged this as the field's leading concern.
- **Guardrails as upfront architecture, not a patch.** The talk's contribution is framing safety constraints as a first-order architectural decision for member-facing health AI — not something added after launch once problems surface.

**[From Ambient Documentation to Clinical Intelligence — Chaitanya Asawa, Abridge](https://www.youtube.com/watch?v=u6q-byPWUuo)**
Chaitanya Asawa of Abridge describes how addressing "pajama time" — the roughly two hours clinicians spend writing visit notes after work — opened a path from ambient documentation into clinical intelligence, reaching 300 of the largest US health systems in two to three years.

- **"Pajama time" is the entry point.** Clinicians spending ~2 hours per day on after-hours note-writing is a concrete, universal pain point that justifies adoption before any broader AI capability is added — and one where the value is immediate and measurable.
- **300 health systems in two to three years.** The documentation product alone reached 300 of the largest US health systems, suggesting it addressed a near-universal problem rather than a niche workflow.
- **Everything in healthcare is downstream of a single conversation.** Asawa's framing positions the doctor-patient encounter as the root of all clinical and administrative data — and argues that the administrative machinery was built around that conversation rather than derived from it.
- **The notes become the foundation for clinical intelligence.** The conversation data captured for documentation purposes is the raw material for moving from reactive note-writing to proactive, structured clinical insight.
