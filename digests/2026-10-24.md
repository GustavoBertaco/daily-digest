## AWS What's New

**[Amazon Connect Customer now supports customizing the Customer Profiles app on the agent workspace](https://aws.amazon.com/about-aws/whats-new/2026/10/connect-customer-customize-cp)**
Amazon Connect Customer Profiles now lets administrators configure which customer data agents see in the workspace and how it is displayed, using layouts built in Profile Explorer. Agents handling different request types can have tailored views combining contact history with data from multiple sources, reducing irrelevant information during interactions.

**[AWS Continuum for code vulnerabilities is now generally available](https://aws.amazon.com/about-aws/whats-new/2026/10/aws-continuum-for-code-vulnerabilities-is-now-generally-available)**
AWS Continuum for code vulnerabilities is now generally available, discovering, validating, prioritizing, and remediating code vulnerabilities at machine speed. It builds a context graph from the AWS environment — resource topology, identity relationships, and network reachability — to surface only findings that carry real business risk and ingests existing security tooling results.

**[Amazon OpenSearch Serverless now supports a 5-second default refresh interval](https://aws.amazon.com/about-aws/whats-new/2026/10/amazon-opensearch-serverless-supports-5-second-refresh-interval/)**
Amazon OpenSearch Serverless reduces the default refresh interval from 10 seconds to 5 seconds for both search and vector collections, making newly ingested documents searchable twice as fast. The change applies automatically to existing collections with no configuration changes required.

**[AWS CloudFormation now simplifies stack update rollback operations](https://aws.amazon.com/about-aws/whats-new/2026/10/aws-cloudformation-cdk/)**
AWS CloudFormation now completes an update rollback in a single force rollback operation even when some resources cannot roll back automatically, returning the stack to a known good state without manual intervention. The operation works across the AWS CLI, SDKs, CDK, and AI agents.

**[Amazon SageMaker AI announces training session APIs for serverless model customization](https://aws.amazon.com/about-aws/whats-new/2026/10/training-session-apis-on-sagemaker-ai)**
Amazon SageMaker AI serverless model customization now supports training session APIs, giving teams full control over post-training algorithms — including SFT, DPO, and custom reinforcement learning methods — without provisioning or managing GPU infrastructure. Teams can write their own training loop while SageMaker handles the underlying compute.

**[AWS Direct Connect announces 100G expansion in Bangalore, India](https://aws.amazon.com/about-aws/whats-new/2026/10/aws-direct-connect-100g-bangalore/)**
AWS expanded 100 Gbps dedicated connections at its Direct Connect location in the Netmagic DC2 data center near Bangalore, India. The location now provides private network access to all public AWS Regions (except China), GovCloud Regions, and AWS Local Zones.

## AI Engineer

**[A Bank Trained Its Own Foundation Model to Catch Fraud — Freddy Lecue, Wells Fargo](https://www.youtube.com/watch?v=UB6hoWyh3B0)**
Freddy Lecue describes how Wells Fargo pre-trained a transformer from scratch on billions of customer transactions — not words — producing a single backbone fine-tuned across fraud detection, credit line decisions, anti-money laundering, and marketing.

- **Transaction-native pretraining changes the vocabulary.** The model learns to predict the next transaction, where tokens are amounts, timing, merchants, and zip codes — not text. Building that token representation from tabular data is described as the hardest part of the project.
- **One backbone, many fine-tuned heads.** Rather than building separate models for each use case, the same pre-trained foundation is fine-tuned per task, reducing the cost and time of adding new financial applications.
- **Demonstrated uplift on fraud.** The model caught more fraudulent transactions than the prior approach — the snippet notes this but the specific uplift numbers are not available in the excerpt.
- **Tokenizing tabular financial data is the central engineering challenge.** Converting structured columns into sequences a transformer can learn from — not adapting a language model — is what separates this from typical LLM fine-tuning work.

**[How to Let AI Agents Sign Up for Your App Safely — Isabelle Williams, WorkOS](https://www.youtube.com/watch?v=uTrY8slys0w)**
Isabelle Williams presents a set of patterns for making a web app agent-ready — covering the authentication handshake, anonymous exploration mode, and identity assertions — demonstrated live with a travel app where an agent signs up, plans a trip, and books dinner autonomously.

- **auth.md as the agent entry point.** An open file at a known path tells agents how to get access to the app, analogous to robots.txt but for authentication flows.
- **Anonymous mode separates trying from committing.** An agent can explore the app and complete work before a human claims it, decoupling discovery from sign-up friction.
- **ID-JAG identity assertions remove form-fill.** The agent's provider vouches for the user's identity, letting the app skip the signup form entirely for users arriving via a trusted agent.
- **End-to-end live demo validated the pattern.** An agent signed up, planned a trip, and booked dinner without human input, showing the full flow works in practice.

**[Don't Trust Your AI Agents. Test Them Like a Scientist — Stephanie Jarmak, Omni Analytics](https://www.youtube.com/watch?v=A3FL_zTQKU0)**
Stephanie Jarmak, drawing on experience building a large coding benchmark at Sourcegraph and evals at Omni Analytics, argues that most agent evaluations are misread and applies scientific experiment design to make them reliable.

- **Harness choice swamps the signal.** Swapping only the evaluation harness moved results by 30% — meaning the tooling decision can dominate the measurement, obscuring actual agent performance.
- **Public benchmarks are for shortlisting, not decisions.** They're useful for narrowing candidates but should not drive production choices; purpose-built evals matched to your actual tasks are required.
- **Treat evals as experiments, not spot checks.** Reliable evals use realistic tasks, repeated runs, full traces, and a metric that maps directly to the outcome you care about.
- **Quality gates turn evaluation into a control system.** Jarmak covers gating mechanisms that block degraded agents from progressing, framing evaluation as continuous control rather than periodic reporting.

**[Why AI Startups Will Disappear Without Compute Markets — Evan Conrad, San Francisco Compute](https://www.youtube.com/watch?v=Wk2bUUGFC_o)**
Evan Conrad explains how San Francisco Compute evolved from an AI lab subleasing its own GPU cluster to survive into both a cluster operator and a compute marketplace, and argues that GPU access, deposit timing, and demand unpredictability are all facets of one underlying credit-and-risk problem.

- **AI companies hit credit limits before power limits.** Upfront deposits eat the bank balance, clusters arrive late and break, and demand is nearly impossible to predict — these compound into a balance sheet crisis faster than any technical bottleneck.
- **Scarcity forces over-commitment.** Because everyone is sold out, new labs and inference companies commit to more capacity than they need, then must sublease the excess to stay liquid — inadvertently building a market.
- **Operating clusters and running a market are the same job.** San Francisco Compute discovered this by necessity: subleasing spare capacity led directly to operating clusters for others, which created the infrastructure for a broader compute market.
- **Demand unpredictability is the structural root cause.** The hardest problem is not finding GPUs but predicting how much inference demand a product will generate, making any fixed capacity commitment a bet on utilization.

**[Better AI Models Won't Fix Your Engineering Team — Nicholas Arcolano, Jellyfish](https://www.youtube.com/watch?v=Ve2bAarPA2I)**
Nicholas Arcolano uses data from approximately 50,000 engineers at 447 companies to decompose what actually drives AI coding throughput, finding that model choice accounts for under 1% of variance in merged PR output.

- **The model explains almost nothing.** Tool choice accounts for under 1% of throughput variance. Company and team account for about 12%. The individual engineer explains most of the remainder.
- **Skill use matters more than having the skill.** Heavy users of AI coding tools see roughly a 30% throughput bump, but that skill-use factor only explains about 3% of total variance — most engineers never use the tools heavily enough to realize the gain.
- **Token usage is a stronger signal than tool choice.** How much an engineer actually interacts with the AI tool (token usage) explains about 9% of variance, significantly outpacing which model they are using.
- **Top performers stay top performers.** Engineers who were already high output before AI tools remain high output after — AI amplifies existing capability rather than redistributing it.
- **One number:** when Cursor pushed many users onto Grok, merged PRs barely moved, empirically confirming that model swaps produce near-zero measurable effect on team output.
