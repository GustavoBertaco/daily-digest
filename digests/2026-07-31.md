## AWS What's New

**[Amazon EC2 Auto Scaling now supports Instance Refresh in CloudFormation](https://aws.amazon.com/about-aws/whats-new/2026/07/ec2-auto-scaling-instance-refresh-cloudformation)**
EC2 Auto Scaling Instance Refresh is now available as a CloudFormation update policy. Configuring the new AutoScalingInstanceRefresh policy causes CloudFormation to trigger an Instance Refresh automatically when properties requiring instance replacement are updated, with capabilities including replace root volume, launch-before-terminate, alarm-based monitoring, and checkpoints with bake time for controlled rollouts.

**[Amazon Redshift Data API announces long polling, session management, and flexible batch execution](https://aws.amazon.com/about-aws/whats-new/2026/07/amazon-redshift-data-api-longpolling-listsession-flexiblebatchexecute/)**
The Redshift Data API gains three new capabilities: long polling (which holds a synchronous response until a SQL statement reaches a terminal state, eliminating repeated polling), session management for visibility into active sessions, and flexible batch execution that allows batch statements to run on separate transactions rather than a single one.

**[AWS Glue announces VPC support, filter pushdown, and partition support for the REST API connector](https://aws.amazon.com/about-aws/whats-new/2026/07/aws-glue-rest-connector-filtering-partitioning-vpc)**
The Glue REST API connector now supports VPC connections, filter pushdown, and partition support. Together these let ETL pipelines connect securely to private REST endpoints, transfer only the data they need, and parallelize reads — enabling ingestion from proprietary systems and emerging platforms that lack native Glue connectors.

**[AWS WAF adds pre-parse text transformations and new text transformations](https://aws.amazon.com/about-aws/whats-new/2026/07/aws-waf/)**
AWS WAF now supports pre-parse text transformations for query arguments and ten new text transformations usable in any rule statement. Pre-parse transformations normalize the raw query string before WAF parses it into key-value pairs, closing HTTP parameter pollution and parser differential evasion gaps; up to ten transformations can be chained per rule.

The service addresses the challenges customers faced when interconnecting workloads across AWS and OCI, supporting multicloud strategies driven by interoperability requirements, technology choice, and deployment flexibility.

**[Amazon Connect Customer now automatically finds example agent evaluations for tailored coaching](https://aws.amazon.com/about-aws/whats-new/2026/07/amazon-connect-customer-example-evaluations-for-agent-coaching/)**
Amazon Connect now automatically surfaces examples of an agent's past evaluations when a manager prepares coaching feedback. The examples highlight recent sessions where the agent scored high or low on the selected coaching topic, along with human or AI evaluator notes explaining the behaviors that drove those scores.

**[Amazon EFS now supports cross-account Replication in AWS GovCloud (US)](https://aws.amazon.com/about-aws/whats-new/2026/07/amazon-efs-cross-account-replication-aws-gov-cloud-us)**

**[Your Finance Agent's Bottleneck Is You — Ramana Siddanth Emani, Auditoria AI](https://www.youtube.com/watch?v=z0sh8HyTrDo)**
The talk argues that in production finance agent development, the developer in the loop is the slowest component — and that the same agent infrastructure used to build products can be turned inward to automate the developer's own workflow.

- **The bottleneck is the developer, not the infrastructure.** Model performance and GPU capacity are not what slow production finance agent shipping. The developer's own iteration loop is the constraint, and the talk reframes developer productivity as an agent-engineering problem.
- **Agent harnesses can be self-referential.** The same tooling teams use to give agents product capabilities can automate the developer's own tasks — coding agents serving the engineers, not just the end users.
- **Parallel git worktrees as a concurrency primitive.** Running an army of coding agents across separate git worktrees lets them clear tasks in parallel, with skills enforcing consistent patterns across each worktree.
- **Tasks feed from existing systems.** Rather than requiring a separate task specification layer, tasks flow into coding agents from where they already live — QA reports, Jira, and similar tools.

**[Build for the Memo, Not the Demo — Shawn Chan, China Resources Holdings](https://www.youtube.com/watch?v=tJFjeMBKbIY)**
After fifteen years and roughly 200 investment committees on decisions at the $100M scale, Shawn Chan has watched AI-generated decks enter the room — and his finding is that AI reliably produces demo quality while failing the memo test.

- **Demo vs. memo is the core frame.** A demo is polished and confident, built to impress. A memo survives a room whose entire job is to find what breaks. AI-generated materials currently optimize for demo quality.
- **AI decks are confidently wrong.** The pattern Chan observes: AI-generated outputs feature cleaner formatting, are never defensive, and are confidently wrong — a combination that is particularly dangerous in high-stakes decision rooms.
- **Pattern recognition from 200 committees.** Chan can spot the flaw fast. The talk uses that accumulated experience as a lens for evaluating where AI outputs succeed and fail under adversarial scrutiny.
- **The danger is credibility, not weakness.** AI outputs are compelling, well-formatted, and confident — which makes it harder, not easier, for decision rooms to identify the flaws they contain.

**[Let's integrate AI Agents in Event-Sourced Systems — Divakar Kumar, FlyersSoft](https://www.youtube.com/watch?v=o6U_2vd967Y)**
In payments and fraud, rule-based engines and ML models handle the clear cases — but there is a gray zone of ambiguous transactions that neither can resolve. Kumar targets that gap with an agentic layer built on top of, not replacing, an existing event-sourced architecture.

- **The gray zone is the target, not the whole system.** Most transactions are already scored cleanly. The agentic layer is specifically for the ambiguous middle cases that sit outside what both the rule engine and the ML model can handle.
- **Additive, not replacement, architecture.** The agent layer sits on top of the existing event-sourced system rather than replacing it, preserving existing bounded contexts — transaction, device, and account — and composing from them.
- **Event sourcing provides natural agent context.** Event-sourced systems capture the full history of state changes, giving the agentic layer a rich, auditable source of context for reasoning about ambiguous decisions.

**[Wearing the Agent: From Group Chats to Glasses — Sai Krishna Rallabandi](https://www.youtube.com/watch?v=s67bE2Ur3bY)**
Nearly every agent today is built for a single user. Rallabandi has spent eight months finding what breaks when a personal agent is deployed into a real group chat — and eventually onto wearable glasses.

- **One-user assumption is the root bug.** Current agent design assumes a single user throughout. Group deployment immediately surfaces problems that don't exist in single-user settings.
- **Multi-user memory is the first hard problem.** With days-long conversations across multiple people, the agent must track who said what and surface only what is contextually relevant without bloating its context window.
- **Security is the second hard problem.** Multi-user agent deployment introduces security challenges absent from single-user architectures; the talk identifies this as the second fundamental constraint alongside multi-user memory.
- **Wearable deployment as the next frontier.** Moving the group agent from chat to glasses adds a physical, ambient dimension that surfaces new constraints around context surfacing and interaction design.

**[We Vetted 2000 AI Skills Before They Reached Developers — Lucas Palma, Nubank](https://www.youtube.com/watch?v=iKQ78wyJEXU)**
Inside a regulated bank, every AI skill shared between engineers is a supply chain risk. Nubank's security team built Skill Vector as a vetting gate between skill creators and the internal marketplace, combining deterministic and LLM-based checks before anything reaches developers.

- **AI skills are a new supply chain surface.** A skill is code handed to a model to extend its capabilities. At engineering scale, sharing skills across teams creates the same supply chain risk profile as sharing packages or container images — compounded here by a regulatory context.
- **Two-pass vetting: deterministic then LLM.** Skill Vector first runs deterministic checks (e.g., detecting destructive shell commands), then passes to an LLM for contextual analysis that rule-based checks miss. The layered structure limits the attack surface of the vetting pipeline itself.
- **The marketplace gate is structural.** Skill Vector sits between the skill author and the internal marketplace, so nothing reaches developers without clearing both passes — vetting is enforced by the system, not left optional.
- **2,000 skills vetted before reaching developers.** The scale makes manual review infeasible and validates the automated pipeline as a necessity rather than a supplement.

**[How Kepler Built Verifiable AI for Financial Services — Vinoo Ganesh](https://www.youtube.com/watch?v=Tt2kX2sgQio)**
Finance runs on deterministic work — arithmetic, attribution, audit trails — that language models are structurally ill-suited for. Kepler's response is to treat the LLM as one component inside a deterministic substrate that makes every figure traceable.

- **LLMs are the wrong tool for arithmetic.** The starting point is structural: LLMs are probability machines optimized for next-token prediction, not deterministic calculation. Kepler routes around this rather than trying to fix it.
- **The provenance problem is primary.** In finance, a number is worthless until you can say where it came from. Every figure Kepler outputs must be traceable — not just plausible.
- **The architecture rests on three tenets.** The first is atomic provenance — making every figure traceable to its origin rather than merely plausible.
- **Hybrid architecture over pure LLM.** The model handles language and reasoning; the deterministic substrate handles math and the audit trail. The LLM is one part of the system, not the whole answer.

**[Persona Engineering: A Field Guide to AI Synthetic Personas — Ishan Anand, InsightSciences.ai](https://www.youtube.com/watch?v=YnNF55QV0zs)**
LLM agents can match human survey respondents closely and produce cleaner data — but that smoothness is the problem. The very noise they eliminate is what makes a real population real.

- **Matching humans isn't the goal — it's the warning sign.** A roughly thousand-person survey replayed by LLM agents produced close matches to human responses with less noise. Lower noise looks like an improvement until you recognize the noise was signal.
- **Synthetic respondents over-smooth the variance.** A real population is messy because it contains genuine divergence. A synthetic respondent averaging across learned patterns cannot reproduce that messiness, producing data that is systematically too coherent.
- **Prompt sensitivity is a major fragility.** Nudging one variable in the prompt template causes purchase probability to swing, because the model infers latent confounders that no one explicitly specified in the prompt design.
- **A field guide to failure modes, not a blanket rejection.** The talk maps where synthetic personas break — distinguishing contexts where the approach is sound from those where it systematically misleads.

**[Why Off-the-Shelf AI Doesn't Understand Money — Udi Menkes, Intuit](https://www.youtube.com/watch?v=Owb8g3yDyzo)**
Generic LLMs give fluent, confident, generic financial answers — Intuit's thesis is that financial AI requires domain-specific models grounded in the history of what similar businesses actually did, not just what text on the internet says about finance.

- **Fluency masks ignorance of business context.** Off-the-shelf LLMs produce confident answers to financial questions but lack knowledge of the specific business or what comparable businesses have done historically.
- **Custom LLMs beat general-purpose on accuracy and latency.** Intuit's domain-specific models outperform general-purpose LLMs on accuracy for financial questions while cutting latency in half, at the scale of 100M+ customers.
- **Accuracy is the foundation, not the destination.** Better accuracy and lower latency are table stakes. The talk's focus is on where financial intelligence goes when AI stops merely reporting what happened.

**[SimulationMaxxing: How we ship agents 20× faster — Aman Gupta (Nubank) + Shreya Rajpal (Snowglobe)](https://www.youtube.com/watch?v=KMR_RBoCa4M)**
Nubank's scale — 135 million customers — makes agent errors expensive. The talk leads with the outcome (five agents in production, roughly 20x faster shipping, higher customer satisfaction) and works back to what unlocked it: simulation-based evals replacing real conversation data.

- **20x shipping speed via simulation-based evals.** Five support agents in production with roughly 20x faster shipping and higher customer satisfaction. The central lever is simulated data standing in for real conversations during evaluation.
- **Multi-turn, stateful evals are the hard part.** Single-turn Q&A evals don't capture agent failure modes that emerge across conversation turns. The talk explicitly contrasts multi-turn agent evaluation with the simpler single-turn paradigm.
- **Simulated data solves the eval data bottleneck.** Real agent conversations are slow and expensive to collect at sufficient volume for good evals. Simulated data fills that gap without waiting for production traffic.
- **Scale makes poor evals unacceptable.** With 135 million customers, a support agent that mishandles conversations fails at a scale that makes simulation-first evals non-negotiable.

**[Skills are new features: Building Skill-Centric Harness — Yogendra Miraje, FactSet](https://www.youtube.com/watch?v=7jjudsEhBtM)**
When skills were open sourced, FactSet reframed their unit of delivery from features to skills. The talk is a practical walkthrough of the patterns that make a skill-centric architecture work at the routing and registry level.

- **The unit shift: features to skills.** The team stopped thinking about shipping features and started thinking about shipping skills — a reframe with architectural implications for how capabilities are organized and exposed to agents.
- **Routing lives in the name and description.** Each skill's heart is a short skill.md whose name and description are routing signals. Distinct names cause correct skill triggering; blurred names cause wrong selection or silence.
- **Progressive disclosure limits context bloat.** The agent loads only the skills it needs rather than the full registry, keeping context windows manageable as the skill count grows.
- **Minimal registry as the starting primitive.** Miraje walks through a minimal skill registry design, suggesting the team built upward from a simple base rather than over-engineering discovery from the start.
