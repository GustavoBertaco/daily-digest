## Meta Engineering

**[Catching Bugs Before They Land: JiTTesting's Human-on-the-Loop Approach at Full Scale](https://engineering.fb.com/2026/10/29/security/catching-bugs-before-they-land-jittestings-human-on-the-loop-approach-at-full-scale/)**
Meta has been using large language models to generate just-in-time tests — called Catching JiTTests — that catch bugs at code-review time rather than after a change lands in production. The system is now in production and a full deployment paper has been released.

- **Just-in-time test generation catches bugs at review, not post-merge.** Each code change triggers LLM-generated tests designed specifically for that diff, addressing the risk that new complexity introduced by a change goes untested.
- **Human-on-the-loop, not human-in-the-loop.** The "Catching" framing distinguishes this from fully automated blocking: developers remain in the loop to accept or reject generated tests, preserving judgment while scaling coverage.
- **From experiment to production impact.** Over the last year Meta moved from initial sharing of the approach to full production deployment, with the results and positive impact now documented in a public paper.

- **GPU selection and latency targets are the core engineering problem.** Abitbol covers the specific latency thresholds that keep engineers satisfied and the hardware choices required to hit them, making this an infrastructure decision as much as a model decision.
- **88% faster on the same hardware through tuning.** Optimization work on the serving stack yielded an 88% throughput improvement without additional GPUs — a significant finding for teams constrained by capital cost.
- **EU regulatory compliance shaped the architecture.** Operating as a regulated bank under EU frameworks required specific decisions around data residency and model governance that would not apply to most tech companies but are increasingly relevant as regulated industries adopt AI coding tools.

**[We Trust AI Agents That Break Every Day - Shy Ruparel, Temporal](https://www.youtube.com/watch?v=mJ7q8CuVmbw)**
Temporal's State of Development survey found that 80.8% of engineers use agents daily but only 49.1% run them in production — a gap Shy Ruparel attributes to four structural failures: usage vs. production, trust vs. reality, prototype vs. enterprise, and seeing vs. recovering from failures.

- **The usage-to-production gap is the real metric.** More than 80% daily usage alongside less than 50% production deployment means widespread experimentation has not translated into operational trust — the unsolved problem is reliability, not capability.
- **Four gaps, not one.** Ruparel's framework separates the engineering and organizational dimensions: usage/production, perceived/actual trust, prototype/enterprise scale, and visibility/recovery — each requiring a different intervention.
- **Durability demos the reliability argument concretely.** A $2,500 payout workflow built with a local model that survives worker termination mid-flight — without losing state, repeating tool calls, or re-spending tokens — makes the abstract case for durable execution tangible.
- **State survival is the distinguishing feature.** The demo's design specifically targets the failure mode that erodes production trust: an agent that can be interrupted and resume correctly from where it stopped, rather than retrying from the beginning.

**[Why a One-Line Change Can Break Your Whole Stack - Cole Gannaway, Qodo](https://www.youtube.com/watch?v=YqxpPI7YUjE)**
Code generation is accelerating faster than review capacity, and the bottleneck has shifted to catching the downstream blast radius of changes that pass all tests. Cole Gannaway of Qodo demonstrates how a single data model change can silently break web, mobile, CLI, and MCP clients simultaneously.

- **Tests passing is not the same as nothing breaking.** A one-line data model change that satisfies the test suite can still break multiple client surfaces — the gap is that tests verify intended behavior, not unintended downstream coupling.
- **A software graph makes blast radius queryable.** Mapping repository relationships into a graph turns "what does this change affect?" from a tribal knowledge question into a structured query, surfacing clients and integrations that aren't obvious from the diff.
- **Tribal knowledge and PR comments are codifiable rules.** Gannaway's approach converts reviewer expertise — the patterns that experienced engineers flag in comments — into automated custom rules that run before review, scaling institutional knowledge.
- **The agent that wrote the code shouldn't grade it.** Gannaway argues for independent review agents separate from the generation agent, framing self-review by the same model as a structural conflict of interest in automated pipelines.

**[How Anthropic Merges 30,000 Code Changes a Day - Manish Kapur, Sonar & Addy Osmani, Anthropic](https://www.youtube.com/watch?v=AnsXWH2_EBU)**
Anthropic scaled from approximately 2,500 to 30,000 merged code changes per day using Claude for first-pass review backed by real verification evidence — and Manish Kapur and Addy Osmani frame this as the shift from "light" software factories (human-authored, AI-assisted) to "dark" ones (agent-authored, human-supervised).

- **12x throughput requires architectural changes to review, not just tooling.** Going from ~2,500 to 30,000 daily merges required rethinking how review confidence is established — Claude doing first-pass review supported by verification evidence rather than just model output.
- **Verification evidence is the trust primitive.** First-pass review by an LLM is insufficient on its own; attaching test results, static analysis, and other verification artifacts to the review gives human reviewers something concrete to evaluate, not just model opinion.
- **"Light" vs. "dark" factories is a useful mental model.** The distinction frames a spectrum from today's AI-assisted human work to near-future agent-authored work with human oversight at the factory level rather than the PR level.
- **Every loop in the factory needs independent, multi-layered verification.** Both speakers emphasize that as agent velocity increases, verification cannot be optional or single-layered — each step in the pipeline needs its own independent check.
- **Labeling agent-written PRs is an open organizational question.** The lightning round surfaces the unresolved question of whether PRs authored by agents should be marked as such and what that means for accountability and review standards.

**[AI That Hunts Logic Bugs Before Attackers Do - Taylor Luttrell-Williams, Sonar](https://www.youtube.com/watch?v=UW8Qkk7MG8A)**
Pattern-based SAST tools catch syntactically bad code but miss logically flawed code that passes all checks — broken access control, business logic gaps, and authentication bypasses. Taylor Luttrell-Williams introduces SonarQube's Hunter Agent, which maps a repo, runs three specialist agents, and adversarially validates every finding.

- **The class of bugs SAST misses is the dangerous one.** Access control failures, business logic errors, and authentication gaps are valid code that does the wrong thing — they require semantic understanding of intent, not pattern matching against known bad patterns.
- **Three specialist agents plus adversarial validation.** The Hunter Agent architecture separates discovery, analysis, and validation into distinct agents, with an adversarial validation step designed to reduce false positives before surfacing findings.
- **46 issues found in a live Python demo.** The demo produced 46 findings, including a privilege escalation path (a user who can make themselves admin) and an MFA bypass — categories that would not surface in conventional SAST.
- **Sonar joining the OpenAI Daybreak cyber partner program.** The partnership positions the Hunter Agent within a broader ecosystem of AI security tooling, though the practical implications for users depend on how the integration is exposed.
