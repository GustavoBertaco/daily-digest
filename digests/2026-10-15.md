## AI Engineer

**[Rebuilding CI for AI-Scale Commit Volume — Gautam Korlam, SonarSource](https://www.youtube.com/watch?v=7b9tov5Uc5s)**
Coding agents now generate pull requests faster than merge queues can process them — Gautam Korlam draws on his work building Uber's SubmitQueue and Gitar (now at Sonar) to examine how CI infrastructure designed for human commit rates becomes the binding constraint in an agentic workflow.

- **The constraint shifts from generation to integration.** When agents produce PRs at volume, the bottleneck moves from writing code to the queue that tests, reviews, and merges it — a fundamentally different scaling problem than human-authored commits.
- **Merge queues weren't designed for agent arrival rates.** A merge queue tests combinations of in-flight changes to protect the main branch, but its throughput assumptions break when arrivals are machine-paced rather than human-paced.
- **Failed builds become the new bottleneck.** Faster code generation means more build failures per unit time, shifting engineering effort toward repeated repairs rather than forward progress.
- **Review economics change under agent volume.** With agents producing many PRs, the human review step becomes proportionally more expensive — CI and code-review pipelines need rethinking before agents can deliver their full throughput benefit.

**[The Cost of Accessibility in AI — Jemima Abu, CAIS](https://www.youtube.com/watch?v=ZccJsdOE54M)**
Jemima Abu runs a direct comparison — the same Figma implementation prompt with and without an accessibility skill — and finds the accessible run costs 58% less and finishes in about a third of the time, then immediately cautions against over-generalizing from a single uncontrolled experiment.

- **58% cost reduction, roughly 3x speed improvement.** The accessibility-guided run was both cheaper and faster, a counterintuitive result that challenges the default assumption that accessibility adds overhead.
- **Abu is explicit about the experiment's limits.** A single uncontrolled comparison cannot prove that accessible development is always cheaper — the value is in surfacing a specific failure mode, not establishing a universal rule.
- **Agents over-engineer when native elements would suffice.** The core failure mode: an agent invents a verbose custom component when a native HTML element could supply much of the required behavior. The accessibility skill steers the agent toward the simpler, semantically correct path.
- **Skills as cost-reduction guardrails.** The accessibility skill functions as a constraint that reduces unnecessary complexity rather than adding it — reframing what "skill" means in agent tooling.

**[Your Fridge Is a Valid Payment Device — Eleonora Drykina & Nina Žižakić, In The Pocket](https://www.youtube.com/watch?v=gonAewBZxfU)**
Building a RAG assistant over roughly 270 PDFs and 6,000 pages of payment rulebooks for an anonymous Belgian payments client, Drykina and Žižakić surface the core challenge: answer-bearing information in financial regulations is often locked inside tables whose structure must survive chunking intact.

- **Table-heavy compliance documents break naive chunking.** Much of the answer-bearing content in payment rulebooks lives in tables — losing table structure during indexing means losing the answers themselves.
- **Section paths and chunk order are first-class metadata.** Their indexing pipeline preserves section paths and chunk order, enabling reconstruction of larger passages that span multiple chunks when a query demands it.
- **CSV conversion preserves relational structure.** Tables are converted to CSV while retaining the relationship between headers and data — a practical technique for making tabular content retrievable.
- **Query scope is unpredictable.** A payment rules question might need one table row, an entire section, or multiple rulebooks — the retrieval layer must handle this variance without the user specifying scope.

**[What Technical Due Diligence Finds When the Deck Says "70% Automated" — Soukaïna Abelhad](https://www.youtube.com/watch?v=gDRCpTMCqEU)**
Soukaïna Abelhad presents a diligence framework for interrogating automation percentage claims in AI pitch decks, starting with a labor-scaling check that requires no model expertise and surfaces whether a product is genuinely removing labor or merely assisting it.

- **The first test needs no ML expertise.** Compare workload growth against the fully loaded labor required to deliver it — if output scales with proportionally more reviewers, trainers, escalations, and rework, you're looking at assistance, not automation.
- **A percentage without a denominator hides the truth.** "70% automated" obscures what's counted and what human work remains; asking what's in the numerator and denominator forces a meaningful, auditable claim.
- **Proportional labor growth is the tell.** More output with proportionally more downstream human effort — review, QA, escalation — signals that the AI is an input to human labor rather than a replacement for it.
- **Ask who checked the result.** The quality verification step is often the hidden labor sink; if humans must validate every AI output, the automation claim becomes substantially narrower.
