## AWS What's New

**[AWS Elastic Disaster Recovery introduces Recovery Plans for orchestrated application recovery](https://aws.amazon.com/about-aws/whats-new/2026/08/elastic-disaster-recovery-plans/)**
AWS Elastic Disaster Recovery (AWS DRS) now offers Recovery Plans, automating the sequential launch of multi-server applications during recovery events and drills. Instead of launching servers individually and tracking dependencies by hand, teams define the recovery sequence once and trigger the entire orchestration with a single action — addressing the common challenge of ordered startup dependencies across databases, application tiers, and supporting services.

**[Amazon Cognito adds admin API operation to reset user TOTP configurations](https://aws.amazon.com/about-aws/whats-new/2026/08/amazon-cognito-totp-reset/)**
Amazon Cognito now provides an admin API to reset a user's TOTP MFA configuration, letting administrators remove the association for a lost device so the user can enroll a replacement on next sign-in. This eliminates the need to recreate accounts for locked-out users while still allowing MFA enforcement to remain active.

**[Amazon Connect Customer now supports unplanned shrinkage in agent schedules](https://aws.amazon.com/about-aws/whats-new/2026/08/amazon-connect-customer-unplanned-shrinkage/)**
Amazon Connect now lets managers input unplanned shrinkage — covering absences such as late logins and unplanned sick leave — directly into agent schedules, giving a more accurate picture of actual staffing. Metrics including scheduled headcount, net staffing, and projected service level update immediately; for example, if 10% of scheduled agents are absent, the adjusted figures reflect that shortfall at once.

**[Mountpoint for Amazon S3 adds memory usage controls](https://aws.amazon.com/about-aws/whats-new/2026/08/mountpoint-for-S3-adds-memory-usage-controls)**
Mountpoint for Amazon S3 can now cap its memory usage, either automatically based on the environment it runs in or via a user-defined limit. Previously, Mountpoint's memory footprint could expand over time with usage patterns, potentially causing performance or stability issues when sharing a memory budget with intensive applications such as machine learning training or analytics workloads.

## AI Engineer

**[How to Generate Mergeable Code with a Context Engine — Peter Werry, Unblocked](https://www.youtube.com/watch?v=qdAkxLoYNI8)**
Peter Werry of Unblocked argues that agents reading a codebase suffer from the same "satisfaction of search" failure radiologists face — finding one plausible answer and stopping — because access to information is not the same as understanding it.

- **Access to information is not understanding.** Attach a wiki to an agent and it will search, land on something plausible, and quit — missing what a practitioner would have caught by holding broader context in their head.
- **The satisfaction of search failure mode.** Radiologists who find one pathology stop scanning; agents that find one viable code answer stop exploring — both miss adjacent signals that would have changed the output.
- **Humans were the context layer before agents.** Developers previously absorbed discussions, code history, and institutional knowledge themselves; agents inherit the information surface but not the integration of it.
- **The argument is about mergeability, not generation.** The talk targets the gap between code an agent produces and code that integrates cleanly into a shared codebase — a distinction most code-gen evaluations don't measure.

**[Can LLMs Write Fast Multi-GPU Kernels? — Simran Arora, Together AI](https://www.youtube.com/watch?v=pOvWgX7IJsc)**
Simran Arora from Together AI shows that as GPU compute has outpaced inter-node communication bandwidth, the performance bottleneck in large AI workloads has definitively shifted to the network — and standard PyTorch and NCCL baselines now fall below 50% of their communication-aware roofline on most problems.

- **The hardware gap is real and compounding.** From A100 to B200, BF16 tensor core throughput improved 7.2x but inter-node communication improved only 2x — the disparity has pushed the bottleneck off the chip entirely.
- **Standard baselines waste more than half of available headroom.** A PyTorch and NCCL baseline lands below 50% of the communication-aware roofline on most problems — the default setup is not a safe starting point for performance-sensitive workloads.
- **Intra-node and inter-node scale differently.** Intra-node bandwidth improved 3x vs. inter-node's 2x — topology decisions about which nodes communicate with which are now a first-class engineering concern.
- **The LLM-for-kernels question is the frame.** The talk investigates whether LLMs can help write the optimized multi-GPU kernels needed to close the performance gap — positioning AI-assisted kernel engineering as a live research frontier.

**[KV Cache-Aware Routing and P/D Disaggregation on Kubernetes — Yuchen Fama & Ashish Kamra, Red Hat](https://www.youtube.com/watch?v=YXowceUKYJI)**
Yuchen Fama and Ashish Kamra of Red Hat expose the gap between published inference benchmarks and real agentic workloads — where sessions span up to 3,000 turns, cache hit rates routinely clear 90%, and input-to-output token ratios often exceed 100:1 — and walk through the routing levers that matter when the client controls the cache lifecycle.

- **Benchmarks are blind to real agentic workloads.** Public numbers report steady-state from sanitized runs; actual session distributions spanning a few turns to 3,000, cache reuse above 90%, and heavily prefill-dominated token ratios are all invisible in standard comparisons.
- **Cache hit rates above 90% make KV-cache-aware routing a primary lever.** At this level of reuse, routing requests to nodes that already hold a session's KV cache state is not an optimization — it is a core architectural concern.
- **Input-to-output ratios of 100:1 make P/D disaggregation necessary, not optional.** Standard benchmarks assume more balanced ratios; prefill-dominated workloads push prefill/decode disaggregation from theory into production necessity.
- **Client-side cache control flips the routing problem.** When the client — not the server — manages the cache lifecycle, routing must track where live KV state actually resides across the cluster.
- **An opening request at about 3 seconds anchors the live demo.** The concrete latency point makes the routing improvement observable rather than theoretical.

**[Building GTM AI Agents: Lessons from Deploying to 6,000 Users — Sait Izmit, Snowflake](https://www.youtube.com/watch?v=DrTdD-ttjCY)**
Sait Izmit of Snowflake deployed a GTM AI agent to 6,000 users by starting with a 150-question benchmark drawn from the actual sales process, scoring 50% on the first run, and then applying a single governing rule: answer fewer questions at higher quality rather than more at lower quality.

- **Start with the eval, not the agent.** Izmit wrote 150 questions from the real sales process before building anything — engineering's objection that the data wasn't connected was the point. The gaps were exactly the problem to solve.
- **Quality over coverage governs everything.** 50 questions at 95% accuracy beats 100 questions at 70%, because a chat interface is judged on its first five answers and a rep who bounces is far more costly than a question the agent declines.
- **First impressions in internal tools are asymmetrically expensive to fix.** The rule is not just about accuracy metrics; it is about the cost of recovering a voluntary adopter who had a bad first experience — winning them back costs far more than the initial failure.
