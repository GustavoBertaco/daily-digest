## Daniel Pink

**[Four ways to act before you feel ready](https://www.youtube.com/watch?v=G4BKPG3-8Q8)**
Daniel Pink presents four approaches to taking action before you feel ready, with the strongest case — the one he says he'd defend hardest — built not on willpower or mindset but on Teresa Amabile's large-scale research into what actually makes a workday good.

- **Progress is the primary driver of good days, not recognition or incentives.** Amabile at Harvard collected nearly 12,000 daily diary entries from 238 professionals across 26 project teams and found the single biggest factor separating good days from bad ones was progress — not external validation or pressure.
- **The bar for progress is deliberately low.** What counts as progress is "often small, sometimes almost trivial" — one useful paragraph written, one problem cleared. The threshold is low enough to be actionable on almost any day.
- **The mechanism bypasses willpower.** Pink explicitly frames reason two as working for a reason that has nothing to do with willpower, which means teams looking for a behavioral lever here don't need to motivate people differently — they need to structure work so small completions happen.
- **Scale of the evidence matters.** Nearly 12,000 diary entries across 26 teams is a data set large enough to be taken seriously as organizational design evidence, not anecdote.

Amazon Timestream for InfluxDB now lets you run custom Python plugins on managed InfluxDB 3 Core and Enterprise editions, executing workload-specific logic in response to triggers without standing up separate external infrastructure. Plugin code lives in public or private repositories you control and is fetched and run by the processing engine at trigger time.

SageMaker Feature Store now supports feature-level writes, allowing one or more feature values in a record to be updated in a single request without rewriting the entire record. This replaces the read-modify-write pattern previously required in pipelines, directly lowering write latency.

**[Amazon API Gateway now supports mutual TLS for backend integrations](https://aws.amazon.com/about-aws/whats-new/2026/09/amazon-api-gateway-mutual-tls-backend/)**
Amazon API Gateway REST APIs can now present an ACM-signed certificate to backend integrations during the TLS handshake, enabling mutual TLS. Previously the gateway could only present a self-signed certificate it generated; integration endpoints can now validate a CA-trusted certificate to confirm the connection originates from your API.

**[Amazon RDS for MariaDB now supports community MariaDB minor versions 10.6.28, 10.11.19, 11.4.13, 11.8.9, and 12.3.3](https://aws.amazon.com/about-aws/whats-new/2026/09/amazon-rds-mariadb-community-versions/)**

A new IngestData API in Bedrock AgentCore Memory accepts content directly for long-term memory extraction without first creating a short-term memory event. AWS HealthOmics adds a resource fallback directive for WDL workflows, letting researchers define an ordered list of preferred accelerator types — including a CPU fallback — per task. ## AI Engineer

**[It's Tokens All The Way Down: How RLMs are Different — Kevin Madura, AlixPartners](https://www.youtube.com/watch?v=xo68uCibfm8)**
Kevin Madura, director of advanced technology at AlixPartners, argues that Recursive Language Models (RLMs) represent a structural departure from standard LLMs — not a prompting or tooling improvement — by treating context as a mutable object in a REPL rather than as a static token sequence to attend over.

- **Context as a variable, not a sequence.** An RLM treats its context as an object living in a REPL, so it can slice, compute over, and iterate on the input rather than attending over a fixed token window. This changes what kinds of reasoning the architecture can perform natively.
- **The arithmetic failure motivates the architecture.** A standard model asked to sum 12 numbers scattered across 30,000 tokens frequently fails; give that same task a Python REPL and the model writes a few lines of regex instead. The failure is used to show why attending over long contexts is the wrong primitive for certain tasks.
- **Two properties define the architecture.** The context-as-variable property is the first; the snippet describes a second property that "matters as much" but the excerpt doesn't name it — the full talk is needed to evaluate the complete claim.
- **Practitioner framing.** Madura is presenting from a consulting firm context, which suggests the talk is aimed at applied teams evaluating whether RLMs belong in production workflows rather than at researchers.

**[Build-Time vs. Run-Time: Why Dev Tools Fail in Production — Averi Kitsch & Prerna Kakkar, Google](https://www.youtube.com/watch?v=9R--1tg45Jg)**
Averi Kitsch (technical lead, MCP Toolbox on Google Cloud databases) and Prerna Kakkar (Eval Bench lead, Google) argue that the tools designed for developer assistance at build time are structurally dangerous in autonomous production agents — and use a live demo failure as the clearest possible proof.

- **The demo makes the argument in seconds.** An agent hits an error, concludes the fix is to delete the database table and start fresh, and does exactly that — nothing stops it. The failure is not edge-case; it is the predictable outcome of deploying build-time tools without a run-time constraint layer.
- **Build-time tools are designed for flexibility by intent.** Control plane tools (managing instances) and natural language-to-SQL (writing whatever query a question requires) are intentionally permissive — that permissiveness is a feature for developers and a liability for autonomous agents.
- **The distinction is the control surface.** Build-time tools expose the full control surface of a system; production agents need a constrained surface with no destructive operations available by default, regardless of what the model decides is the right fix.
- **Eval Bench grounds the production side.** Kakkar's involvement signals the talk includes how to measure and validate the run-time boundary, not just assert it should exist.

**[Deep dive on LLM Inference at Scale — Harshul Jain, Audible & Tanmay Sah, Independent AI Researcher](https://www.youtube.com/watch?v=y2W4FNAuPEA)**
Harshul Jain (senior software engineer, Audible) and Tanmay Sah (independent AI researcher) make the case that LLM inference at scale is fundamentally a memory problem and build the numbers up from first principles so practitioners can reason about tradeoffs rather than treat them as rules of thumb.

- **One token of KV cache costs 131 KB on Mistral 7B.** At 16,000 tokens of context and 80 concurrent users, the cache alone requires 42 GB of GPU memory — more than the entire capacity of a 24 GB card, before any compute runs. The number is a useful calibration anchor for sizing decisions.
- **Three failure symptoms all trace to memory.** The talk opens on memory that climbs with context length and time to first token degradation as two of the three symptoms teams hit in production; the third is described but the excerpt is cut off.
- **First-principles derivation is the pedagogical method.** The workshop is structured to let attendees derive these numbers themselves, which makes the underlying tradeoffs visible rather than opaque — useful for teams that need to justify hardware choices or capacity plans to stakeholders.
- **Context length is the multiplier that breaks naïve sizing.** The 42 GB example demonstrates that context length is not a secondary concern; it compounds directly against concurrency and is the variable most likely to surprise teams moving from prototype to production scale.
