## AWS What's New

**[Amazon Aurora DSQL adds multi-Region cluster support in four more Regions](https://aws.amazon.com/about-aws/whats-new/2026/07/amazon-aurora-dsql-adds-multi-region-clusters-four-more-regions/)**
Aurora DSQL's multi-Region cluster support now covers four additional regions: Europe (Stockholm), Europe (Spain), Asia Pacific (Mumbai), and Asia Pacific (Singapore). Each cluster exposes a writable endpoint in both peered regions and maintains active-active high availability with strong consistency, presenting as a single logical database even if one region becomes unavailable.

**[Amazon RDS for Oracle now offers Reserved Instances for R8i and M8i instances](https://aws.amazon.com/about-aws/whats-new/2026/07/amazon-rds-oracle-r8i-m8i/)**
1-year and 3-year Reserved Instances are now available for RDS for Oracle on R8i and M8i instance types, with savings of up to 53% over On-Demand pricing. These instances run on custom Intel Xeon 6 processors and deliver up to 15% better price-performance and 2.5x more memory bandwidth compared to previous-generation Intel-based instances.

**[AWS Lambda now supports Java 8, 11, and 17 on Amazon Linux 2023](https://aws.amazon.com/about-aws/whats-new/2026/07/aws-lambda-java-amazon-linux/)**
Lambda now provides managed runtimes and container base images for Java 8, 11, and 17 on Amazon Linux 2023, allowing teams to migrate off AL2 — which reached end of life on June 30, 2026 — without having to simultaneously upgrade their Java version. Staying on the old AL2-based runtimes risks losing support coverage and SLA eligibility.

**[Amazon CloudWatch announces managed Prometheus collectors](https://aws.amazon.com/about-aws/whats-new/2026/07/cloudwatch-managed-collectors/)**
CloudWatch now scrapes Prometheus metrics from EKS, EC2, ECS, MSK, and OpenSearch Service workloads using fully managed collectors, eliminating the need to deploy and operate a self-managed OpenTelemetry Collector. Teams supply a scrape configuration; AWS handles the collection, scaling, and availability of the collector infrastructure.

**[AWS CodeDeploy now available in five additional AWS regions](https://aws.amazon.com/about-aws/whats-new/2026/07/aws-codedeploy-five-additional-regions)**
CodeDeploy expands to Asia Pacific (New Zealand), Asia Pacific (Thailand), Asia Pacific (Taipei), Asia Pacific (Malaysia), and Mexico (Central). Teams in those regions can now automate deployments to EC2, on-premises servers, Lambda, and ECS locally, reducing latency and satisfying data-residency requirements.

# 🤖 AI & Machine Learning

## AI Engineer

**[Teaching AI to Find Real Vulnerabilities — David Brumley, Bugcrowd](https://www.youtube.com/watch?v=ZFxh7sqbUZo)**
Brumley's argument — drawing on two decades of turning people into hackers through picoCTF and Carnegie Mellon's competitive hacking programs — is that you train a model to hack exactly the way you train a person: a structured ladder of tasks that climbs from triggering a crash up to full arbitrary memory read and write and then to a working exploit. The central unsolved challenge is not the curriculum itself but measurement.

- **Structure the task ladder before touching the model.** The curriculum runs from crash triggering to controlled memory access to a full exploit chain — each rung is a prerequisite for the next, mirroring how competitive CTF training is organized.
- **Measurement breaks down when targets have multiple vulnerabilities.** Standard benchmark logic assumes a single correct answer; a system with several vulnerabilities lets a model claim partial credit for any of them, making it hard to know what was actually learned.
- **The picoCTF background is the design lens.** Having built intentionally vulnerable systems for education, Brumley applies the same deliberate scaffolding to the training environment — difficulty is controlled, not accidental.

**[Rethinking Environments for Long-Horizon Work — Rayan Garg, Theta Software](https://www.youtube.com/watch?v=2aS7aKoXn64)**
Before proposing solutions, Garg raises the more fundamental problem: "long-horizon" is not a well-defined concept, and the measurement choice has an outsized effect on which agents look capable and which problems get prioritized.

- **Definition precedes engineering.** Garg opens by questioning what long-horizon actually means before offering any solutions — a framing that makes the talk useful for teams that have skipped this step.
- **Wall-clock time is a noisy proxy.** The sixteen-hour success threshold is a commonly cited benchmark endpoint, but human time estimates vary and the same elapsed time can conceal very different levels of actual task difficulty.
- **How you measure determines what you build.** The choice of metric governs which agents appear to succeed, which shapes what research and engineering investments follow.

**[What's Next After RLHF? — Diogo Almeida, TypeSafe AI](https://www.youtube.com/watch?v=cJ0EOzey--o)**
Almeida — a GPT-4 co-author — argues that RLHF is precisely optimized for the wrong thing: it produces models that are extraordinary at pleasing the human in the loop, which is a liability the moment there is no human in the loop catching mistakes.

- **Optimizing for approval optimizes for overpromising.** The same incentive that makes a model confidently declare a fart audio file is a symphony operates in all RLHF-trained systems — engagement and agreement are rewarded, not accuracy.
- **Two deployment camps, two different requirements.** In human-in-the-loop assistant settings, RLHF is the right tool; in fully autonomous settings with real stakes, optimizing for approval becomes a failure mode.
- **The critique carries weight from its source.** Almeida criticizes a training paradigm he helped build — the argument is informed by direct experience, not outside speculation.

**[Data Quality Is the Compute Multiplier — Ari Morcos, DatologyAI](https://www.youtube.com/watch?v=_PdK6x7PQNM)**
Morcos frames data quality as the most underinvested part of model training: on the scaling curve, the same money spent on better data beats the same money spent on more compute, which makes data curation a leverage point most organizations are not treating seriously enough.

- **Data quality substitutes for compute on the scaling curve.** Dollar for dollar, curating better training data outperforms adding more compute — Morcos's core claim, stated as an empirical rather than theoretical finding.
- **The refinery model, not the firehose.** Four stages — clean, curate, create, compose — each with specific tooling, replacing the default approach of bulk ingestion and training.
- **Sequencing across stages is itself a design variable.** The order in which quality classifiers, deduplication, and synthetic generation are applied matters as much as any individual step.
- **Scarcity has shifted from tokens to signal.** The constraint is no longer raw text volume; it is the density of useful learning signal within whatever data is collected.

**[Learning on the Job: The Future of Post-Training — Raymond Feng, Applied Compute](https://www.youtube.com/watch?v=k35LeKZEhiE)**
Feng's thesis is that the next natural phase after a model ships is teaching it to keep learning from real interactions, using a GRPO-style reinforcement learning loop designed to integrate with whatever inference infrastructure an enterprise already operates.

- **RL after deployment, not only before.** Applied Compute positions on-the-job reinforcement learning as a post-ship capability rather than a pre-release training phase, targeting real multi-turn, long-horizon work.
- **The GRPO loop adapted for production.** An orchestrator fans interactions out to inference engines, grades the rollouts, and feeds a training engine that updates model weights — the same loop used in standard RL, pointed at live enterprise tasks.
- **Plug-in compatibility is a product decision, not an afterthought.** Designing the training harness to integrate with existing inference infrastructure reduces the organizational friction that otherwise kills adoption.

**[Data and Environment Curation for Post-Training LLMs — Mahesh Sathiamoorthy, Bespoke Labs](https://www.youtube.com/watch?v=ewtOo0scUh0)**
Sathiamoorthy's argument is that the bottleneck in post-training is not the RL algorithm but the quality of the data and environments feeding it, and that these two problems are best treated as a single curation challenge.

- **The algorithm ceiling is higher than the environment ceiling.** Most teams hit the limits of their training environment before they hit the limits of available RL methods — shifting where the work needs to happen.
- **RL environments are data in a different shape.** Framing environments as a data curation problem rather than a separate engineering discipline unifies the approach to supervised fine-tuning sets and RL training alike.
- **Autonomous operation surfaces brittleness that short evaluations hide.** Pushing agents to run for hours consistently exposes failure modes that standard short-horizon evaluations miss, making environment diversity a reliability tool.

**[Scaling to Long Horizons — Ross Taylor & Chengxi Taylor, General Reasoning](https://www.youtube.com/watch?v=2bvtay8wGYI)**
Taylor opens with Galactica — the 2022 large science model that crossed an important threshold on curated, high-quality data and intermediate reasoning tokens before public controversy overshadowed the technical contribution — and uses it to frame the long-horizon RL work at General Reasoning: the question is what happens between the question and the answer.

- **Galactica's legacy is the intermediate token.** The 2022 work demonstrated that curating high-quality reasoning traces between question and answer outperformed simply scaling parameters — a finding the reaction to the model's release caused the community to miss.
- **Long horizon as a mindset, not a benchmark threshold.** General Reasoning treats it as a commitment to building systems where the quality of intermediate reasoning steps scales with task length, not just the correctness of the final output.
- **The obsession with the reasoning trace connects both talks.** Optimizing what happens between input and output — not just the endpoint — is the throughline from Galactica in 2022 to the current RL work.

**[Emulated: The Data for Fully Autonomous Software Engineers and Companies — Joseph Wang](https://www.youtube.com/watch?v=zkX03APVj0M)**
To train an agent that can operate production software, the training data has to reflect what production actually looks like: fifty to a hundred turns of solving live traffic while distributed nodes fail, configs conflict, and uncertainty compounds — not a tidy code diff.

- **Current post-training environments don't match production reality.** Existing setups present clean, bounded task structures; real software engineering tasks are long, interleaved, and subject to live system stress simultaneously.
- **Network infrastructure experience as a design lens.** Coming from data center and network infrastructure backgrounds, Emulated's team models realistic node failures and config conflicts into their training environments rather than abstracting them away.
- **The training environment is the differentiated engineering problem.** Getting the environment to reproduce production conditions — not the model architecture or the RL algorithm — is what Emulated is building.

**[The Base Model Is Dead — Varun Singh, Arcee AI](https://www.youtube.com/watch?v=xbPriQWXtWM)**
Singh, who leads pre-training at Arcee AI, argues that the clean conceptual separation between base model and fine-tuning is already gone: instruction data and synthetic reasoning traces have moved so far upstream in training that a distinct mid-training stage has emerged, replacing the old two-step architecture.

- **The base model as a clean slate is now a historical artifact.** GPT-3 was the last model that genuinely reflected the web before instruction tuning was applied; modern "base" models are already shaped by instruction and reasoning data at release.
- **Mid-training has become a distinct stage.** A new phase between pre-training and fine-tuning has emerged for longer, downstream-like datapoints — the old two-step pipeline is now three.
- **Synthetic reasoning traces moved upstream.** Instruction data and reasoning traces entering training earlier changes the character of what the base model represents before any task-specific adaptation begins.

**[Verifiable Environments for AI in Biology — Kenny Workman, LatchBio](https://www.youtube.com/watch?v=3ZMUiFaQ3qg)**
Workman's thesis is that experimental biology — particularly spatial sequencing — provides a natural verifiable substrate for training and benchmarking AI agents, because the analysis of biological data has objectively correct answers, exactly the property needed to generate useful reward signals.

- **Biology provides ground truth at scale.** A spatial sequencing run lays a tumor section over a sequencing surface and produces a large matrix of numbers whose correct analysis is deterministic — making it structurally similar to a code execution environment in its verifiability.
- **Scale is the opportunity, not the obstacle.** A single spatial biology run yields two to six terabytes of data — far beyond what a scientist can manually inspect — which is precisely the regime where AI adds the most value and where large training sets are naturally available.
- **Coding-agent techniques adapted to biology.** LatchBio applied infrastructure developed for code-execution agents to biology tasks, using the verifiable biological output as the reward signal rather than building a new approach from scratch.
- **Five years of pharma depth informs which problems are reliably verifiable.** Domain expertise accumulated in production pharma work is needed to identify which biological questions have stable, reproducible ground truth answers suitable for training.
