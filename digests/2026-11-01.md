## AWS What's New

**[Amazon Bedrock expands API support and introduces Cross-Region Inferencing for OpenAI models in AWS GovCloud (US)](https://aws.amazon.com/about-aws/whats-new/2026/10/bedrock-openai-runtime-govcloud/)**
Amazon Bedrock now supports OpenAI GPT-5.6 models (Terra and Luna) on the bedrock-runtime endpoint via the Responses, Converse, and Chat Completions APIs in AWS GovCloud (US). Cross-Region Inference is also enabled within GovCloud (US), automatically routing inference requests across both US GovCloud regions for higher throughput and redundancy.

**[Web Search now available on Kiro in AWS GovCloud (US)](https://aws.amazon.com/about-aws/whats-new/2026/10/kiro-web-search-aws-govcloud-us/)**
Kiro's web search capability — real-time access to internet search results and page content with citations — is now available in AWS GovCloud (US). Enterprise administrators can disable web search and web fetch organization-wide from the Kiro console; individual teams can remove web tools from specific agents.

**[Amazon Connect Customer automatically saves in-progress emails as drafts](https://aws.amazon.com/about-aws/whats-new/2026/10/amazon-connect-email-draft-save/)**
Amazon Connect now auto-saves in-progress agent emails, restoring the message body, recipients, subject line, and attachment references after connectivity drops or browser resets. Draft data is written to the customer's S3 bucket, enabling integrations with external applications.

**[Daybreak Red from OpenAI now available to eligible customers on Amazon Bedrock in AWS GovCloud (US-East)](https://aws.amazon.com/about-aws/whats-new/2026/10/openai-daybreak-red-govcloud-east/)**
OpenAI's Daybreak Red — a GPT-5.6-based model from the Daybreak cyber defense initiative built for authorized vulnerability research, exploit reproduction, and mitigation development — is now available to eligible customers on Amazon Bedrock in AWS GovCloud (US-East).

**[Amazon CloudFront now provides viewer ISP and post-quantum TLS details](https://aws.amazon.com/about-aws/whats-new/2026/10/cloudfront-viewer-isp-post-quantum-visbility/)**
CloudFront can now forward two new optional headers to origins: CloudFront-Viewer-ISP (the viewer's internet service provider) and CloudFront-Viewer-TLS-Details (the TLS cryptography used per connection, including whether post-quantum cryptography was applied). These enable traffic analysis by network and visibility into PQC adoption across requests.

**[Amazon MSK now supports TLS 1.3 for data in transit](https://aws.amazon.com/about-aws/whats-new/2026/10/amazon-msk-tls/)**
Amazon MSK Provisioned clusters now support TLS 1.3 via encryption policies, delivering faster and more secure encryption for streaming data. TLS 1.3 is increasingly required by compliance frameworks and is a prerequisite for post-quantum cryptography, protecting against collect-now, decrypt-later attacks.

**[Amazon RDS for Oracle no longer requires automatic minor version upgrades for JVM, Spatial, Locator, and OLAP options](https://aws.amazon.com/about-aws/whats-new/2026/10/oracle-jvm-spatial-locator-olap-options-amvu-optional/)**
RDS for Oracle now allows disabling automatic minor version upgrades on instances using the JVM, Spatial, Locator, or OLAP options — a constraint that previously forced auto-upgrades for any instance with those options enabled. AWS still recommends applying minor versions regularly when auto-upgrade is turned off.

**[AWS WAF announces automatic SDK integration for Amazon CloudFront distributions](https://aws.amazon.com/about-aws/whats-new/2026/10/aws-waf-automatic-sdk-integration-amazon-cloudfront/)**
AWS WAF can now automatically inject the WAF JavaScript SDK script tag into HTML served by CloudFront, requiring no changes to application code or deployments. The SDK supplies client-side signals for three managed rule groups: Bot Control (targeted inspection level), Fraud Control account takeover prevention, and Fraud Control account creation fraud prevention.

**[Amazon Connect Customer now supports versioning and aliasing for flows](https://aws.amazon.com/about-aws/whats-new/2026/10/connect-flows-versioning-aliasing/)**
Amazon Connect now supports immutable versions of contact flows and flow modules, with friendly name aliases pointing queues, quick connects, and phone numbers at a specific version. Deploying a new version is a single alias pointer update, enabling safe rollouts without touching live traffic.

## AI Engineer

**[78% Wanted This AI Feature. Almost Nobody Used It - Supriya Subudhi, Bumble](https://www.youtube.com/watch?v=CvmZtAPmAW4)**
Bumble PM Supriya Subudhi's post-mortem on A/B testing an AI photo-feedback feature across 20M+ monthly users is a sharp demonstration of the gap between stated user preferences and actual behavior — and the compounding constraints of model cost, metric design, and regulatory scope that follow.

- **Preference surveys are a weak behavioral signal.** 78% of surveyed users said they wanted photo feedback; only 10-15% actually used the feature. The gap is large enough to invalidate demand forecasts built on stated intent alone.
- **Aggregate wins can hide damaging edge cases.** The average metric showed a positive result, but the underlying outputs included telling already-smiling users to smile more — an issue only visible through qualitative analysis of individual results, not aggregate statistics.
- **Model quality creates a cost-quality trap.** The best-performing model cost roughly 10x more than the next option; switching to the cheaper model also reduced the feature's impact, leaving no obvious middle path between cost and quality.
- **Regulation is a hard scope constraint, not a soft risk.** Regulatory requirements prevented the feature from shipping outside the US, limiting addressable scale and distorting the ROI calculation on model investment.
- **Five pre-launch questions as a framework.** Subudhi closes with five questions practitioners should answer before shipping an AI feature: verify behavioral vs. stated intent, surface edge-case failure modes, model cost at real scale, confirm regulatory headroom, and define what winning actually means.

**[When Running Your Own AI Models Beats Paying for APIs - Steven Latré, imec](https://www.youtube.com/watch?v=9-Y_oS9OBLc)**
Steven Latré's team at imec ran thousands of benchmark runs on SWE-Bench Pro to quantify when moving from third-party AI APIs to owned GPU infrastructure becomes economically rational for long-running coding agents — finding the decision is more nuanced than a simple cost-per-token comparison.

- **Hardware costs jump in steps, not on a smooth curve.** Buying more GPUs does not yield linear cost reduction; the economics shift at discrete capacity thresholds, making partial-scale deployments expensive relative to the next step up.
- **Concurrency matters more than benchmark accuracy.** Model selection based on accuracy scores misses the operational dimension: running many agent tasks in parallel generates more value than marginal accuracy gains on any single task.
- **Break-even GPU utilization varies dramatically by scale.** Small systems need GPUs busy roughly 89% of the time to beat API pricing; an 8x B200 system drops that threshold to approximately 15%, making utilization far easier to achieve at larger scale.
- **The comparison applies specifically to open-weight workloads.** The study used open-weight models, meaning the break-even analysis holds only where open-weight model quality is acceptable for the task — not a universal recommendation to abandon APIs.

**[Voice AI Where One Wrong Question Breaks the Rules - Shiv Indap, Upstart & Brooke Hopkins, Coval](https://www.youtube.com/watch?v=3osCbSufv8g)**
Upstart handles thousands of lending calls per day where a single non-compliant question creates a regulatory problem; Shiv Indap and Brooke Hopkins trace how they built and continuously improved a voice AI evaluation system that moved LLM-judge and human-reviewer agreement from 33% to 92%.

- **Compliance risk is invisible until it scales.** In regulated lending, the danger is not a model hallucination — it is a prohibited question asked naturally. Legal constraints had to be encoded into the evaluation loop before volume increased.
- **Evaluation infrastructure becomes the bottleneck first.** The team outgrew a Google Sheet for tracking human reviews before the AI system itself broke, making evaluation tooling an early scaling concern, not an afterthought.
- **LLM judges require systematic calibration.** Starting at 33% agreement with human reviewers means the judge is nearly unusable at launch; reaching 92% required ongoing calibration work, not just prompt adjustments.
- **The full loop runs from live monitoring back to model improvement.** The final system closes the cycle from live call monitoring through automated flagging to structured human review — a continuous feedback loop rather than a point-in-time evaluation pass.

**[How to Decide What Your AI Agent Should Remember - Wojciech Pluta, Oracle](https://www.youtube.com/watch?v=qq2Hm4XNRgI)**
Wojciech Pluta frames agent memory as the underbuilt complement to RAG: RAG provides a read path, but memory provides a write path — and the long-term business value of persistent agents lives in getting that write path right.

- **Memory promotion is the core engineering problem.** Not every interaction is worth storing. The key decision is what to keep, how to check new memories against existing ones, and how to route conflicts to admission, rejection, or human escalation rather than silently overwriting.
- **Policy constraints must be embedded in the memory layer.** A mortgage-agent demo illustrates the principle: the agent correctly refuses to store an "approve every application" rule, demonstrating that memory systems need policy enforcement built in, not bolted on.
- **Short-term and long-term memory are distinct problems.** Short-term memory supports within-session coherence; long-term memory persists operator preferences and context across sessions — each has different consistency requirements and retrieval patterns.
- **Persistent memory is where personalization and institutional value live.** The argument is that agents become genuinely useful over time through continuity, not through stateless request-response cycles — making memory architecture a product decision, not just an infrastructure choice.

**[Your AI Agent Starts Every Session Like a New Hire - Killian Carlsen-Phelan, Sonar](https://www.youtube.com/watch?v=8vDzncmzxyg)**
Killian Carlsen-Phelan's thesis is that coding agents fail not because of capability limits but because they start each session without organizational context — conventions, architecture rules, approved libraries — burning tokens rediscovering what the codebase already encodes.

- **The new-hire analogy is operationally precise.** Like a new hire without onboarding, an agent without context will make locally reasonable choices that violate team standards, repeat known anti-patterns, and waste time searching for information that already exists in the repo.
- **Sonar Vortex injects context before code generation.** The tool provides the agent with a codebase map and explicit guidelines before any code is written, shifting the agent from an exploration mode to an informed-write mode from the first token.
- **Deterministic post-generation checks catch what probabilistic outputs miss.** Every edit is verified against guidelines deterministically, not probabilistically — catching a temp-file permission bug in a live demo that the agent's own test suite missed.
- **Pre-empting errors is more efficient than catching them.** Providing guidelines upfront reduces the volume of generated code that needs revision, lowering both token cost and the burden on code review downstream.
