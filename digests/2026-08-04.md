## AI Engineer

**[MCP Apps: Extending the Frontier — Ido Salomon & Liad Yosef](https://www.youtube.com/watch?v=-jY2T2PiJBE)**
MCP Apps proposes a way for MCP servers to return rich interactive interfaces — buttons, charts, web components — instead of text responses, targeting the mismatch between conversational AI output and tasks where a visual or interactive UI communicates faster.

- **The problem is output format, not capability.** Chat and coding assistants return walls of text; for many interactions a button or chart is the faster path, and MCP Apps targets this gap directly.
- **Architecture: tool call → registered resource → web component.** A tool call links to a registered resource; the MCP host renders it as a web component; clicks flow back into the agent.
- **MCP UI is the foundation.** Liad Yosef co-created the MCP UI project that underlies MCP Apps; the spec is now shaped through an open working group inside the MCP committee.

**[MCP Tasks (async): Why Aren't Any Agents Supporting Them? — Cornelia Davis, Temporal](https://www.youtube.com/watch?v=s4r6nk5WsZw)**
The MCP tasks specification defines how a tool can run asynchronously — persisting through dropped connections, network blips, and process crashes — yet almost no agents implement it. Cornelia Davis, a distributed-systems veteran who wrote the book on cloud native patterns, argues the gap between synchronous tool calls and real-world durable work is exactly what the spec exists to close.

- **Synchronous tool calls break on real workloads.** Invoke-and-wait assumes a stable, fast connection; over time connections drop, networks blip, and processes crash — losing work in flight.
- **MCP tasks are durable by design.** A task can run long, report incremental progress, and pause for human input without losing its place — behaviors impossible in a standard synchronous tool call.
- **Adoption lags despite the spec.** Davis walks through why almost no agents support tasks yet, a concrete gap that grows more consequential as agents take on longer, multi-step work.
- **The speaker's framing carries weight.** Davis wrote the book on cloud native patterns; her argument is grounded in distributed-systems foundations, not agentic hype.

**[When Will The Benchmaxxing Plague End? — Nick Heiner, Surge AI](https://www.youtube.com/watch?v=-npY6XjM8CQ)**
Nick Heiner argues that the very existence of the word "benchmaxxing" — used openly by labs — reveals how far evaluation has drifted from measuring what models actually do. His talk is a field guide to identifying and resisting the antipatterns that quietly break benchmarks.

- **The tell is the vocabulary.** When "benchmaxxing" enters industry parlance and labs use it without embarrassment, teams stop asking whether a benchmark reflects real-world capability.
- **The gap is structural, not accidental.** Every model launch reveals a gap between benchmark numbers and actual performance; Heiner frames this as a predictable result of how benchmarks are designed and used.
- **Antipatterns are the entry point.** The talk maps out the failure modes that quietly break benchmarks, giving practitioners a framework for reading evaluation claims skeptically.
- **The cumulative effect obscures progress.** When teams optimize for scores rather than capability, the result is an "avalanche of numbers" that measures the wrong thing — Heiner's most pointed characterisation of where the field has drifted.
