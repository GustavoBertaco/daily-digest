## AWS What's New

**[Amazon ECS adds Amazon VPC Lattice support for blue/green, linear, and canary deployments](https://aws.amazon.com/about-aws/whats-new/2026/10/amazon-ecs-vpc-lattice-blue-green-deployments)**
Amazon ECS now supports built-in blue/green, linear, and canary deployment strategies for services using Amazon VPC Lattice, enabling managed traffic shifting natively from ECS during rollouts. Applications using VPC Lattice for cross-VPC and cross-account service communication can now control how quickly traffic shifts without external tooling.

**[AWS Health introduces the version catalog for software lifecycle management](https://aws.amazon.com/about-aws/whats-new/2026/10/aws-health-introduces-version-catalog-software-lifecycle-management)**
AWS Health now provides a centralized version catalog that consolidates lifecycle information — end-of-support dates, upgrade paths — for software versions across AWS services, moving customers from reactive to proactive version management. The catalog is available in the AWS Health Dashboard; customers on Business Support Plus, Enterprise Support, or Unified Operations can also access it via the AWS Health API to integrate lifecycle data into operational workflows.

**[Amazon Aurora DSQL now supports partial indexes](https://aws.amazon.com/about-aws/whats-new/2026/10/aurora-dsql-partial-indexes/)**
Aurora DSQL can now index a specific subset of a table using a WHERE clause on CREATE INDEX, storing only qualifying rows rather than the full table and reducing both query latency and index storage cost. The pattern targets tables with a small active working set alongside a large historical tail — such as open orders among years of completed ones — where full-table indexes carry unnecessary overhead.

**[Amazon EKS and Amazon EKS Distro now support Kubernetes version 1.37](https://aws.amazon.com/about-aws/whats-new/2026/10/amazon-eks-distro-kubernetes-version-1-37)**
Amazon EKS and EKS Distro now support Kubernetes 1.37, available immediately for new cluster creation and for upgrades from the EKS console, eksctl, or infrastructure-as-code tooling. Version 1.37 promotes several features and includes bug fixes.

**[AWS Brazil automates distribution of non-Brazilian software product licenses to Brazilian customers](https://aws.amazon.com/about-aws/whats-new/2026/10/aws-brazil-software-license-distribution/)**
AWS Brazil now offers an automated distribution workflow under the AWS Brazil 2P Distribution Program, allowing eligible non-Brazilian ISVs to grant AWS Brazil the right to distribute their SaaS product licenses to Brazilian customers. AWS Brazil acts as seller of record, invoicing customers in Brazilian Reais (BRL) with applicable local taxes and handling seller disbursements and withholding.

# 🤖 AI & Machine Learning

## AI Engineer

**[Your LLM App Returned 200 OK. It Was Still Wrong. — Marina Petzel, Datadog](https://www.youtube.com/watch?v=rTojoVotlD8)**
Classic observability signals — latency, errors, traffic, saturation — confirm an LLM app is running but say nothing about whether it is correct. Marina Petzel, GenAI advocate at Datadog, lays out the additional monitoring categories that production generative AI applications require on top of the golden signals.

- **A 200 OK is not a correctness signal.** The golden signals tell you the infrastructure is up; they do not tell you whether the LLM produced an accurate, safe, or appropriately priced response. Treating uptime as a proxy for quality is a category error with real consequences.
- **Cost monitoring requires tagging discipline before the bill arrives.** Token creep, model drift, and uncached calls can each silently inflate costs; meaningful attribution requires tagging by team, feature, or model variant at the point of call, not after the invoice lands.
- **Safety monitoring is a separate category, not a sub-concern of quality.** Prompt injection, PII leakage, toxicity, and jailbreak attempts require dedicated detection — none of these are surfaced by latency or error-rate dashboards.
- **Quality monitoring closes the loop with hallucination rate.** Hallucination is the signal most directly correlated with whether the app is doing what users expect — the talk treats it as a distinct monitoring category alongside safety and cost, not a subset of either.

**[YOLO Mode, Safely: MicroVM Sandboxes for Any Agent — Rowan Christmas, Docker](https://www.youtube.com/watch?v=OE_lLNCNfQo)**
Harness-level guardrails cannot protect a host machine from a sufficiently capable coding agent — Rowan Christmas demonstrates this by prompt-engineering his own agent into accessing his browser history and financial data in five prompts, then shows how microVM sandboxes provide security by design rather than by policy.

- **Guardrails at the harness layer are the wrong abstraction.** Five prompts were enough to bypass them entirely in a live self-hack; guardrails positioned at the prompt or function-call layer do not bound the agent's access to host resources.
- **Kernel-level isolation is the meaningful boundary.** Docker Sandboxes (sbx) spin up a VM with its own kernel and filesystem isolation, structurally limiting the agent's blast radius regardless of what it is instructed to do.
- **Default-deny networking changes the threat model.** The sbx environment enforces default-deny networking — architecturally different from attempting to enumerate and block dangerous operations after the fact.
- **Secret placeholders prevent credential exfiltration.** The sandbox accepts secret placeholders rather than actual credentials, closing a key exfiltration vector before the agent ever runs.
- **Single-command spin-up is the adoption primitive.** One command creates the isolated VM; reducing that friction is what makes developers actually use sandboxes rather than skipping isolation during prototyping.

**[The 5 Levels of Self-Driving Production — Eric Schwartz, Traversal](https://www.youtube.com/watch?v=y-OVWZD4j6U)**
AI-generated code accelerates development while compounding the difficulty of production debugging — Eric Schwartz argues that root cause analysis is a causal inference problem, not an observability problem, and presents a five-level maturity model for autonomous production operations.

- **More AI-written code means more time troubleshooting.** The relationship is direct: higher code velocity increases the frequency and complexity of production incidents faster than observability tooling scales to handle them.
- **Observability tells you what broke, not why.** Dashboards surface symptoms; understanding causation requires different tooling. Conflating the two leads to alert fatigue without resolution.
- **RCA is a causal problem — the tooling category required to solve it is different from monitoring infrastructure.** This reframing is the talk's central thesis and has practical consequences for how teams budget and build their production operations stack.
- **Real case studies ground the five-level model.** Schwartz covers alert intelligence work for a PepsiCo supply chain team and an incident root cause analysis deployment, moving the maturity framework from abstract to applicable.

**[Lessons from Generating 12 Trillion Synthetic Tokens — Bogdan Gaza, DatologyAI](https://www.youtube.com/watch?v=FQwTqUmcbRg)**
Frontier pre-training is hitting the ceiling of available web text — roughly 30 trillion usable tokens exist on the web, and pre-training demand now exceeds that — forcing synthetic data generation from augmentation to necessity. Bogdan Gaza, co-founder and CTO of DatologyAI, shares engineering lessons from a recent run of approximately 12 trillion synthetic tokens across web, math, and code.

- **The web is a finite pre-training resource.** With roughly 30 trillion usable tokens of web text available, frontier pre-training requirements have outpaced organic data supply, making large-scale synthetic generation a structural requirement rather than an optional augmentation.
- **Rephrasing is DatologyAI's core synthetic data recipe.** BeyondWeb, their approach, generates additional tokens by rephrasing existing web, math, and code content — a recipe choice with implications for diversity and quality of the resulting training data.
- **Infrastructure simplification was a prerequisite for trillion-token scale.** The team migrated from a split Slurm/Kubernetes setup to a unified Ray, KubeRay, and vLLM stack, treating infrastructure complexity itself as a scaling bottleneck.
- **12 trillion tokens is a production benchmark, not a theoretical exercise.** The lessons come from a real run at this scale, making the engineering observations directly applicable to practitioners building similar synthetic data pipelines.

**[Why AI Didn't Actually Make You Ship Faster — Gabriel Spencer-Harper, Meticulous](https://www.youtube.com/watch?v=HLTa7Vcs4X0)**
AI has shifted the software development bottleneck from code generation to verification — Gabriel Spencer-Harper argues that assertion-based tests are structurally unable to keep pace with AI-generated code, and presents a record-and-replay approach to near-exhaustive frontend verification with zero developer authorship effort.

- **Verification, not generation, is now the constraint.** AI writes faster than humans can review; adding more AI coding capacity without fixing the verification layer makes the bottleneck worse, not better.
- **Assertion-based tests can't scale to AI output velocity.** Hand-written tests require the same human time that is already the bottleneck — the mismatch is structural and cannot be closed by writing tests faster.
- **Recording real user flows creates the test baseline automatically.** Meticulous records actual user sessions and replays them on each pull request, bypassing the authorship bottleneck entirely by deriving coverage from production behavior.
- **Visual before/after diffs catch regressions that pass code-level tests.** Comparing rendered output across PRs surfaces frontend regressions that unit and integration tests miss, closing a gap that grows as AI-generated code volume increases.
- **Zero developer effort is the design target.** The system is built so coverage scales without requiring developers to write or maintain test code — addressing the root cause rather than asking the constrained resource to do more.

**[Why 99% Accurate Browser Agents Still Fail — Derek Meegan, Browserbase](https://www.youtube.com/watch?v=5xi_S1f9sDU)**
Compound error rates make per-step accuracy a misleading production metric for browser agents — a 99%-accurate agent succeeds only about 36% of the time over 100 steps. Derek Meegan explains what separates a browser-agent demo from thousands of unattended production runs and argues for measuring success per transaction, not per run.

- **Per-step accuracy is the wrong optimization target.** At 99% per-step accuracy over 100 steps, transaction success rate is roughly 36%; the math demands a different framing.
- **Cost and value are temporally misaligned.** Cost accumulates at every step; value only arrives at a successful final step. Expensive intermediate steps that lead to failure are pure waste with no partial credit.
- **Agents see the web in three modes.** Text, screenshots, and code are the perception channels available; the combination chosen affects both accuracy and per-step cost, and the tradeoffs compound over long task sequences.
- **Measure per-transaction success, not per-run metrics.** Reframing the success metric to end-to-end task completion forces honest accounting of what production users actually experience.
- **The demo-to-production gap is an architecture problem, not a model problem.** What separates thousands of unattended production runs from a polished demo is system design — reliability, recovery, and cost management — not raw model accuracy.

**[Stop Rationing Tokens: Let the Harness Pick the Model — Kimchi by Cast AI](https://www.youtube.com/watch?v=48YUYDjwfYY)**
Token budgets optimize the wrong unit — Cast AI built an open-source coding harness after their coding-agent bill escalated, shifting the cost measurement from tokens to tasks and delegating model selection to the harness rather than constraining what developers can ask.

- **Token limits are the wrong lever.** Capping tokens to control cost cripples developer productivity; the underlying problem is whether each token is being spent on work that completes the intended task, not the volume of tokens consumed.
- **Cost per task is the correct unit of measurement.** Measuring cost per task rather than cost per token aligns the optimization target with actual outcomes — task completion — instead of a proxy metric that can be met while still failing the task.
- **The harness owns model selection.** Rather than hardcoding a model or leaving selection to individual developers, Kimchi's harness selects from both proprietary and open models based on outcome data for each task type, matching capability to need automatically.
- **Open-sourcing the harness removes the proprietary gate.** Cast AI published Kimchi as open source after building it internally to control their own exploding costs, making the cost-per-task approach available to practitioners without licensing friction.
