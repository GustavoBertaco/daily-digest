# 🤖 AI & Machine Learning

## AI Engineer

**[Dashboards Are Dead — Sarah Simionescu, Composio](https://www.youtube.com/watch?v=YiFqcu9YA38)**
Sarah Simionescu, member of technical staff at Composio, makes the case that the monitoring dashboard is an artifact of a pre-agent world — one she herself stopped opening despite logging into Datadog every day for six months. The interface designed for humans staring at charts is the wrong abstraction for agents that need to act on signals.

- **Dashboards lost their users before agents arrived.** Six months of daily Datadog access with zero dashboard opens is the central data point: the work had already moved elsewhere.
- **The path to MCP was progress, but incomplete.** The evolution from five tools and five query languages, through the AI sparkle button, to MCP still leaves fundamental gaps: agents don't learn across sessions, too many tools drown the model's context, and every app remains isolated.
- **MCP alone is not an agent-native interface.** Bolting MCP onto an existing dashboard preserves the wrong mental model; the interface must be redesigned around how agents consume context, not how humans scan charts.
- **The fix is an interface designed for agents.** Simionescu shows what a purpose-built agent interface looks like — the contrast with a traditional dashboard is the core of her talk.

**[Stop Fine-Tuning to Fix Retrieval Problems — Anant Srivastava](https://www.youtube.com/watch?v=qflLT3SoVbw)**
Anant Srivastava, principal technologist for data and AI platforms at Oracle, argues that prompt, memory, and weights are not a ladder you climb when answers go wrong — they are three tools for three distinct jobs. Applying the wrong one does not fix the problem; it creates a new one.

- **Architecture accumulates by accident.** Most AI teams never make a deliberate decision about where their knowledge lives — six months of normal product work makes that decision for them.
- **Fine-tuning is not a retrieval fix.** A support assistant that kept inventing product names after a fine-tune is the canonical failure mode: fine-tuning shapes style and stable behavior, not dynamic knowledge recall.
- **Three tools, three jobs.** Prompt handles current context; memory and retrieval handle dynamic or frequently updated knowledge; weights encode stable behavioral patterns. These are not interchangeable escalation steps.
- **A diagnostic precedes the fix.** Srivastava provides a structured way to identify which layer is actually failing before reaching for fine-tuning as the default.

**[What Makes Open Models Fast in Production — Sujee Maniyam, Nebius](https://www.youtube.com/watch?v=TRe1u7dHYiA)**
Open models have nearly closed the capability gap with proprietary ones; the competitive frontier has shifted to inference efficiency. Dylan Bristot from Nebius Token Factory and developer advocate Sujee Maniyam walk through what it actually takes to serve open LLMs fast and cheaply in production.

- **Capability parity is not cost parity.** Open models can match closed model quality, but matching their latency and cost in production requires deliberate hardware and software engineering — it does not come for free at deployment time.
- **The make-vs-buy decision maps to a specific loop.** The choice between closed APIs and self-hosting is not a one-time call; it runs through the inference → data → post-training → deployment cycle, with different trade-offs at each stage.
- **Layer-by-layer inference optimization is where speed comes from.** Sujee covers the hardware-level optimizations that move the needle, including NVFP4 on the latest NVIDIA hardware as a concrete lever for fast inference.

**[GPU Died. Training Didn't: Self-Healing Training at Scale — Crusoe](https://www.youtube.com/watch?v=bRGyYaE0lxI)**
At thousands of GPUs, hardware failures are a certainty, not an edge case — and fixing them manually at 3 a.m. does not scale. Connor Guerrero, Young Jeong, and Nikhil Gupta from Crusoe describe how they layered Kubernetes under Slurm to build self-healing training infrastructure without requiring researchers to change their workflows.

- **Failure is a design input, not an edge case.** The baseline assumption across thousands of GPUs is that something will fail; the architecture must absorb failures automatically rather than surfacing them as pages.
- **Slurm and Kubernetes solve different problems.** Slurm gives researchers gang scheduling, topology awareness, and familiar sbatch workflows — it falls short on dynamic resource allocation, node health monitoring, and observability. Kubernetes fills exactly those gaps.
- **Neither team changes how they work.** The layered architecture exposes Slurm's surface to researchers and Kubernetes's surface to infrastructure operators — each team keeps its existing mental model.
- **AutoClusters automates the recovery cycle.** The component handles fully automatic recovery, replacing the manual detection-to-restoration loop that previously required human intervention overnight.

**[An Interaction Is All You Need — Ivan Leo, Google DeepMind](https://www.youtube.com/watch?v=8aVbXXvJUY4)**
As models became agents, the stateless per-call completion API became the wrong abstraction. Ivan Leo, developer experience engineer at Google DeepMind, introduces the Gemini Interactions API and Managed Agents — a ground-up redesign of the developer surface around multi-turn, stateful agent interactions.

- **The old API model breaks under agentic workloads.** The progression from single completions to function calling to agents exposed the limits of stateless APIs — developers were left hand-managing thought signatures and turn state between calls.
- **Server-side state is the core change.** Interaction IDs let the server own multi-turn state; developers reference an interaction rather than re-serializing context on every call.
- **Strongly typed multimodal outputs and tool mixing.** The new API enforces output types and allows built-in and custom tools to be combined within a single interaction — removing a common source of fragile glue code.
- **The steps data model captures agent reasoning structure.** A new `steps` abstraction gives visibility into how the agent traverses its reasoning within an interaction, which the original completions API had no equivalent for.
- **Managed Agents raises the abstraction level further.** Built on top of the Interactions API, Managed Agents offers a higher-level entry point for teams who do not need the full low-level surface.

**[I Built a Personal AI Agent on a Raspberry Pi — Jeremy Adams, Neo4j](https://www.youtube.com/watch?v=oUZEt4EiPbk)**
Jeremy Adams, senior developer advocate at Neo4j, demonstrates that a functional personal AI agent requires no cloud infrastructure — he builds one live on stage on a Raspberry Pi 4B worn as a necklace, using open-source components and a graph database for memory.

- **Commodity hardware is sufficient for a full agent stack.** A Raspberry Pi 4B running NanoClaw, messaged over WhatsApp, with Docker-isolated agents proves that resource constraints sharpen architectural choices rather than blocking them.
- **WhatsApp as the entry point reduces friction to zero.** Using an existing messaging interface means no new app, no onboarding — the agent is reachable from any device immediately.
- **Docker isolation protects limited resources.** On constrained hardware, runaway agent processes are a real risk; Docker-isolated agents contain the blast radius.
- **POLE schema for graph memory.** Person, Object, Location, Event — the four-category schema Adams uses in Neo4j to structure the agent's persistent graph memory.
- **Voice-to-text added mid-demo through a USB mic and hardware button.** The modular architecture let Adams wire in an offline voice input channel live, illustrating how loosely coupled the components are.

**[How VS Code Went from Monthly to Weekly Releases with AI — Harald Kirschner](https://www.youtube.com/watch?v=I2LL_wd89-A)**
After ten years of monthly releases, VS Code now ships weekly to more than 50 million users. Harald Kirschner, principal product manager on VS Code at Microsoft, explains that the acceleration was not a consequence of deploying more AI — it required rebuilding the entire delivery system around agent-ready codebases and faster tooling.

- **More AI was not the solution; a rebuilt system was.** The key insight is that speed came from restructuring the codebase and toolchain so agents could be trusted with it — not from adding more agents to an existing process.
- **Agent-ready codebases are a prerequisite, not a side effect.** Agents need to drive the app with confidence; achieving that required deliberate codebase changes before the agents could be productive.
- **TypeScript Go delivered 10x faster builds.** Build latency was a genuine bottleneck for a weekly cadence; the switch to TypeScript Go's compiler removed it as a constraint.
- **Three stages structured the transition.** The talk covers shipping faster (agent-ready codebases, skills, build speed, letting agents drive the app) and what broke along the way across all three stages.
- **50 million users sets the stakes for every systemic decision.** A small team shipping weekly at that scale means the reliability of each change carries as much weight as the release tooling itself.
