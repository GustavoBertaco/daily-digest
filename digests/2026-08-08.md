## AWS What's New

**[Amazon ECS now supports fractional GPU scheduling with Amazon EC2 G6f instances](https://aws.amazon.com/about-aws/whats-new/2026/08/amazon-ecs-fractional-gpu/)**
Amazon ECS now supports fractional GPU scheduling on EC2 G6f instances, allowing containers to run on GPU partitions as small as one-eighth of an NVIDIA L4 Tensor Core GPU with 3 GB of memory. This enables right-sizing for small-model AI inference, model experimentation, and graphics workloads that do not require a full GPU, reducing infrastructure costs compared to full-GPU provisioning.

**[AWS Lambda console extends console-to-IDE integration to Kiro and Cursor](https://aws.amazon.com/about-aws/whats-new/2026/08/aws-lambda-ide-kiro-cursor/)**
The Lambda console's console-to-IDE integration now covers Kiro and Cursor alongside the existing VS Code support, providing a guided setup that preserves Lambda configuration context when transitioning to local development. The expansion broadens the reach of the console-to-IDE workflow to two popular IDEs.

**[Amazon EC2 G7 instances are now available in the AWS Europe (Spain) Region](https://aws.amazon.com/about-aws/whats-new/2026/08/amazon-ec2-g7-available-spain)**
Amazon EC2 G7 instances, powered by NVIDIA RTX PRO 4500 Blackwell Server Edition GPUs, are now available in the Europe (Spain) Region. G7 instances deliver up to 4.6x AI inference performance and up to 2.1x graphics performance compared to G6 instances, and improve performance on GPU-accelerated data analytics workloads.

**[AgentCore runtime instances are now generally available](https://aws.amazon.com/about-aws/whats-new/2026/08/aws-bedrock-agentcore-runtime-instances-generally-available/)**
Amazon Bedrock AgentCore runtime instances are now generally available, letting teams run AI agents on their own EC2 instances without managing the underlying infrastructure. Runtime instances complement the existing microVM-based option and unlock the full breadth of EC2 instance types for sustained, resource-intensive, or specialized-hardware agent workloads.

**[Amazon ElastiCache now supports Graviton4-based M8g, R8g, and C8gn nodes](https://aws.amazon.com/about-aws/whats-new/2026/08/amazon-elasticache-graviton4-m8g-r8g-c8gn/)**
Amazon ElastiCache now supports Graviton4-based M8g, R8g, and C8gn node families for Valkey and Memcached. Compared to equivalent Graviton3-based nodes, Graviton4-based nodes deliver up to 47% higher throughput, up to 43% lower P99 latency, and up to 31% better price-performance for on-demand pricing, with more memory per node as well.

**[AWS Glue Schema Registry is now available in ten more AWS regions](https://aws.amazon.com/about-aws/whats-new/2026/08/aws-gsr-10-more-regions)**
AWS Glue Schema Registry is now available in ten additional regions: Asia Pacific (New Zealand, Thailand, Hyderabad, Osaka, Malaysia, Melbourne, Taipei), Mexico (Central), Israel (Tel Aviv), and Canada West (Calgary). The Schema Registry is a serverless, free feature of AWS Glue that validates and controls the evolution of streaming data using Apache Avro, JSON, and Protobuf schemas.

**[AWS Transform for migrations automates post-launch actions](https://aws.amazon.com/about-aws/whats-new/2026/08/aws-transform-for-migrations-automates-post-launch-actions)**
AWS Transform now automates the configuration and execution of post-launch actions across migration workflows, including multi-account migrations, by applying account-level action definitions automatically to each source server. Actions run through AWS Systems Manager immediately after launch, removing the manual server-by-server configuration work.

**[AWS Security Agent now supports email-based MFA for penetration testing](https://aws.amazon.com/about-aws/whats-new/2026/08/aws-security-agent-mfa/)**
AWS Security Agent (now part of AWS Continuum) can now penetration-test applications that use email-based MFA, including flows that deliver one-time codes or verification links by email — a coverage gap that previously put such applications out of scope for automated pentesting.

**[Amazon RDS now provides visibility into storage volume initialization status](https://aws.amazon.com/about-aws/whats-new/2026/08/amazon-rds-storage-volume-initialization-visibility)**
Amazon RDS now exposes the initialization status of database storage volumes created from snapshots, letting operators determine when storage has reached fully provisioned performance after a restore. This is relevant after point-in-time restores, read replica creation, and Single-AZ to Multi-AZ conversions.

**[Amazon WorkSpaces now publishes enhanced observability metrics](https://aws.amazon.com/about-aws/whats-new/2026/08/amazon-workspaces-observability-metrics)**
Amazon WorkSpaces now publishes additional performance and session health metrics to CloudWatch at no extra cost, spanning network performance, compute and storage utilization, and session lifecycle events. Administrators can use metrics such as TCP retransmission rate to proactively identify and troubleshoot issues affecting end-user experience.

## AI Engineer

**[Local Models: Trust, Control, Optimization — Carter Abdallah, NVIDIA](https://www.youtube.com/watch?v=FWMJQDH3iK0)**
A panel discussion at the AI Engineer conference examines why enterprises are choosing local and open models — not for benchmark performance but because availability can be guaranteed — and what that means for how "trust" in AI systems should actually be defined.

- **Trust as availability, not safety scores.** When Fable lost access to frontier systems, enterprises moved to Chinese open models not because they scored better but because access could be counted on. Lucas Atkins draws a hard line between trust (can you count on the model being there?) and safety — treating them as separate, non-interchangeable properties.
- **Open models are verifiable; closed APIs are not, by construction.** An open model is a directory of files you can inspect running on code you can read. The same trust claim made about a closed API is unverifiable by construction — a categorical difference, not a matter of degree.
- **Arcee reoriented in response.** The transcript excerpt records that Arcee's response was to reorient, but the snippet cuts off before the direction is named.

**[Compression at the Edge — NVIDIA, Unsloth, HuggingFace, Ollama](https://www.youtube.com/watch?v=J4_jCrTxMkk)**
A panel at AI Engineer explores model compression at the edge, revealing that large models are structurally unequal in ways that make aggressive size reduction feasible without proportional quality loss — the key insight being that most parameters in a large model are not doing meaningful work.

- **The super weights finding changes compression calculus.** Quantizing a single critical number in a model can make it 20% worse — meaning compression is not uniformly safe across all parameters. Identifying which weights are load-bearing is the prerequisite to compressing anything safely.
- **86% smaller does not mean 86% dumber.** GLM 5.2 compresses from 1.5 terabytes to 250 GB with quality largely preserved. The gap between size reduction and quality degradation is the core bet compression practitioners are making.
- **Layers are structurally unequal.** The first and last layers carry disproportionate weight; the middle layers barely contribute. This hierarchy is what makes aggressive compression viable — the unimportant layers can be collapsed without touching the ones that matter.
- **Undertrained parameters are free to zero.** A model trained on 30 trillion tokens still leaves many parameters near zero because they were never needed. Those can be set to zero — and thus compressed away — at minimal quality cost.

**[The State of Model Routing — NVIDIA, Cognition, OpenRouter](https://www.youtube.com/watch?v=QHBjufYK8TA)**
A panel at AI Engineer challenges the assumption that routing each task to its highest-benchmark model is the efficient choice, showing that out-of-distribution failure modes can make a cheaper model far more expensive in practice than the model it was meant to replace.

- **Per-task cost inverts per-token cost.** Running terminal bench on Opus and Haiku, Opus scores about three times better at one-tenth the per-task cost, even though Haiku is cheaper per token. The unit of measurement for routing decisions should be task completion cost, not token price.
- **Out-of-distribution thrashing is routing's hidden failure mode.** A small model pushed outside its training distribution enters a loop — calling tools repeatedly until it has cost more than the expensive model would have charged upfront. The cheaper model becomes the more expensive one.
- **Benchmark-based routing is structurally fragile.** Sending each task to whichever model benchmarks best fails the moment a task falls outside the benchmark's coverage — which is exactly when reliable routing matters most. Walden Yan identifies this as the core fragility of that approach.
