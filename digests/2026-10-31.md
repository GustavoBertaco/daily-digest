## Daniel Pink

**[Envy](https://www.youtube.com/watch?v=D2D1ZckdoTQ)**
Stacy S. Kim argues that envy functions as a compass — a reliable signal pointing toward what you actually want — rather than an emotion to suppress or hide.

- **Envy as data, not shame.** The conventional instinct to conceal envy discards a useful signal; Kim's case is that it's worth reading rather than hiding.
- **The envied person as teacher.** The core reframe: whoever triggers your envy is demonstrating what you want, and may be the most relevant model for how to get there.
- **The compass only works if you look.** Treating envy as evidence rather than a moral failing is the prerequisite — acknowledgment is what converts the feeling into actionable direction.

## AWS What's New

**[AWS Glue Data Catalog now supports Apache Iceberg table optimization in the US West (N. California) Region](https://aws.amazon.com/about-aws/whats-new/2026/10/glue-data-catalog-optimizers-us-west-1/)**
AWS Glue Data Catalog now supports automatic table optimization for Apache Iceberg tables in the US West (N. California) Region. Iceberg tables accumulate small files, snapshots, and unreferenced files with each write, slowing queries and increasing storage costs; optimization can be enabled per-table or across an entire Data Catalog.

**[AWS Marketplace now enables partners to list once and sell through multiple subsidiary accounts](https://aws.amazon.com/about-aws/whats-new/2026/10/aws-marketplace-subsidiary-account-authorization)**
AWS partners operating multiple legal entities can now publish a product listing once in a primary account and authorize local subsidiaries to sell it through direct private offers, eliminating duplicate listings. The primary account retains ownership and controls which products each subsidiary can sell and which buyer countries it can target.

**[Amazon RDS for Oracle and SQL Server now support storage autoscaling on additional storage volumes](https://aws.amazon.com/about-aws/whats-new/2026/10/amazon-rds-oracle-sqlserver-autoscaling-additional-storage-volumes)**
Amazon RDS for SQL Server and Oracle now extend storage autoscaling to additional storage volumes (up to three per instance, up to 256 TiB total) with zero downtime. Previously, capacity on those extra volumes had to be provisioned manually based on anticipated workload.

**[Amazon Aurora now supports post-quantum TLS key exchange](https://aws.amazon.com/about-aws/whats-new/2026/10/aurora-postgresql-post-quantum-tls-key-exchange/)**
Amazon Aurora PostgreSQL-Compatible Edition introduces post-quantum TLS (PQ-TLS) key exchange for encrypting data in transit. PostgreSQL versions 18 and higher can configure the ssl_groups parameter to select cryptographic groups from Aurora's allow list.

**[Amazon MSK Connect now supports updating connector plugins and worker configurations](https://aws.amazon.com/about-aws/whats-new/2026/10/amazon-msk-connect-update-plugin-worker-configurations)**
Amazon MSK Connect now allows updating the custom plugin and worker configuration of an existing connector without recreating it. This covers deploying a new version of connector code or changing worker-level settings such as key/value converters and producer/consumer throughput properties.

## AI Engineer

**[Your Agent Just Paid for Nothing: 6 Attacks on x402 Payments - Ishween Kaur, SoFi](https://www.youtube.com/watch?v=YU1uD_YkpjU)**
Ishween Kaur demonstrates how to break x402 — the HTTP-based micropayment protocol for AI agents — by walking through six of twenty vulnerabilities she found in a safe test environment, then showing the specific guard that stopped each one.

- **x402 enables agents to pay for data autonomously.** The protocol routes tiny on-chain payments through HTTP headers, letting agents transact for APIs and data without human-in-the-loop authorization.
- **Six attack classes demonstrated.** Price manipulation in the payment header, double payments, free data extraction, a single payment unlocking many pages, lookalike sellers, and prompt injection that persuades an agent to pay again.
- **Each attack has a traceable guard.** Kaur walks through each failure mode trace by trace, showing detection and mitigation rather than just cataloguing theoretical risks.
- **Prompt injection is a live risk in payment flows.** Attackers can embed instructions in content that convince an agent to pay unnecessarily — agent payment systems inherit all LLM injection vulnerabilities.
- **Twenty vulnerabilities catalogued total.** Safe deployment requires systematic verification at each integration point; the session covers six but the broader attack surface is significantly larger.

**[Why AI Won't Replace Stock Pickers - Jack Woodruff, Candlestick & Vinoo Ganesh, Kepler](https://www.youtube.com/watch?v=y2dyD6slKxE)**
Former Citadel portfolio manager Jack Woodruff and Kepler CEO Vinoo Ganesh argue that AI accelerates the preparatory work of fundamental investing but doesn't eliminate the human judgment at the center of generating alpha.

- **Humans remain the bottleneck.** Even with AI tooling, the limiting factor in investment decisions is human judgment — AI shifts where time goes, not who decides.
- **AI compresses prep, which raises table stakes.** Hours of research preparation can be reduced to minutes, but the same compression is available to every competing fund, lifting the baseline.
- **Auditability is non-negotiable.** Woodruff's rule: never trust a number you can't audit; LLM-generated outputs require independent verification before entering investment decisions.
- **Edge still exists, but the source shifts.** When all funds access the same models, differentiation comes from proprietary data, decision speed, or superior context — not model access.
- **Fund team structures are expected to evolve.** How teams are organized around AI tools is changing, though the conversation holds that the human role in final judgment remains constant.

**[The Cheaper AI Model That Costs You More - Rayan Krishnan, Vals AI](https://www.youtube.com/watch?v=rWtbOgl5FTU)**
Rayan Krishnan of Vals AI explains why single-score model benchmarks hide a "jagged frontier" where the nominally cheapest model per token can produce the most expensive outcomes once task-level performance is measured.

- **Benchmark scores are task-specific.** For finance tasks such as tax analysis and Excel LBO modeling, the best model changes by task — no single model dominates across all work.
- **Cheaper per token can cost more overall.** A nominally cheaper model that burns extra tokens and completes tasks less reliably can flip its apparent cost advantage in practice.
- **A real consequence: $1.5M on tokens in a month.** A case study illustrates the cost of model selection without task-specific benchmarking.
- **Reward hacking distorts leaderboards.** Building reliable benchmarks requires guarding against models that optimize for the metric itself rather than the underlying capability being measured.
- **Multi-turn work is where evals still lag.** Single-turn benchmarks don't capture cumulative error in agentic, multi-turn tasks, which is where production costs actually compound.

**[Catch the Bugs Your Code Review Misses - Killian Carlsen-Phelan & Taylor Luttrell-Williams, Sonar](https://www.youtube.com/watch?v=wP3P89YB9fA)**
Killian Carlsen-Phelan and Taylor Luttrell-Williams of Sonar demonstrate Gitar, a code change verification agent, catching bugs that diff-based code review misses — including logic errors outside the changed lines and unenforced business rules.

- **Diff-based review has a structural blind spot.** Gitar catches a bug not present in the diff — a buyer can refund a ticket after transferring it to a friend — exposing how scope-limited human review is.
- **Business rules need an explicit, enforced home.** A project config encodes the rule "show customers the all-in price"; the agent enforces it on every PR rather than relying on reviewers to remember.
- **Iterative auto-fix until CI passes.** When a CI test fails, Gitar diagnoses the root cause, pushes successive fixes, and auto-merges once the PR is green.
- **Agents operate at the scope of business logic, not lines.** The shift is from "does this change look right?" to "does this change preserve system-level correctness?"

**[Why Humans Can't Keep Up With AI-Written Code - Tariq Shaukat, Sonar](https://www.youtube.com/watch?v=LQW_Wvqhp04)**
Sonar CEO Tariq Shaukat draws on the Toyota/Lexus factory model to argue that AI-generated code requires a systematic quality infrastructure — not faster human review — because code volume now far outpaces human oversight capacity.

- **The volume mismatch is stark.** Lines of code increased 2,450% while releases grew only 30% — human review is already the bottleneck, and the gap is widening.
- **Humans agree with AI-generated errors 4 out of 5 times.** Reviewers anchor to AI output rather than independently verifying correctness, making speed irrelevant as a fix.
- **Errors compound over long agentic tasks.** Error rates that seem acceptable in short tasks multiply when chained, making long agentic runs especially risky without intermediate checkpoints.
- **LLM judges are unreliable at scale.** Using LLMs to evaluate LLM-generated code introduces its own failure modes — a problem without a clean solution yet.
- **Near-zero time to exploit.** Vulnerabilities in AI-written code get exploited faster than in human-written code, further compressing the window for remediation.
