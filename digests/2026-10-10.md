**[Building resilient systems with Sam Newman](https://www.youtube.com/watch?v=a0sZV0qIbI0)**
Sam Newman, who was in the room when the term "microservices" was coined and wrote its most-read book, argues that the pattern is an architecture of last resort — and explains what teams consistently get wrong when they adopt it anyway.

- **Independent deployment is the non-negotiable test.** Newman centers this as the defining property; services that cannot deploy independently are distributed monoliths, not microservices, and they carry extra failure modes without the benefit.
- **Teams reach for microservices for the wrong reasons.** The most common mistake is adopting the pattern because well-known companies use it, rather than because the organizational or technical constraints actually demand it.
- **The link to team autonomy is real but conditional.** Microservices can help teams work more autonomously, but only when the organizational structure already calls for that separation; otherwise they add coordination overhead without the corresponding gain.
- **Being present at the origin of a term matters.** Newman's critique comes from watching a pattern he helped name get cargo-culted across the industry for over a decade.

## Daniel Pink

**[Four questions to help you stop overthinking](https://www.youtube.com/watch?v=hKHUq_uXvzc)**
Research by Sonja Lyubomirsky and Susan Nolen-Hoeksema shows that rumination is a confidence trap: people who dwell on problems produce worse solutions while simultaneously feeling like they gained insight. Four targeted questions break that loop by pulling the mind toward something actionable.

- **Confidence and quality decouple under rumination.** In the Lyubomirsky and Nolen-Hoeksema studies, ruminators' confidence went up while their actual solution quality went down — the feeling of productive thinking is an unreliable signal.
- **Questions beat internal argument.** Each of the four questions pushes the mind out of the loop precisely because questions require a forward-looking answer, rather than a replay of the problem.
- **The trap is stickiness.** Overthinking persists because it genuinely feels like progress; recognizing that feeling as systematically decoupled from quality is the first move toward breaking the pattern.

## AI Engineer

**[Building on the Codex Harness — Dominik Kundel, OpenAI](https://www.youtube.com/watch?v=9WiBJRO84yY)**
Rather than building a new agent harness from scratch, teams can adopt the open-source Codex App Server — the JSON-RPC protocol that already powers the Codex app, IDE extensions, and third-party clients in Xcode and JetBrains.

- **The harness is battle-tested in production.** The Codex App Server is the same infrastructure running the Codex app itself; adopting it means starting from something already shipping at scale.
- **The event stream is observable.** Kundel uses an inspector he built to show the real events flowing between the Codex app and server, making the protocol transparent rather than a black box.
- **Over 120 client messages are configurable.** The harness is not a fixed pipeline — teams have extensive control over what the client-server interaction looks like for their specific use case.
- **Multi-IDE support is built in.** Xcode and JetBrains clients already connect through the same server, meaning cross-environment deployment is a solved problem rather than a bespoke integration.

**[Stop Prompting — Greg Pstrucha, Sentry](https://www.youtube.com/watch?v=E3KbFLAGD6A)**
Re-prompting a coding agent to fix a recurring mistake is a losing strategy: context compaction erases the correction, and the mistake returns. Pstrucha argues teams should codify repeated corrections as tests, strict types, and linter rules instead of repeating the same prompts.

- **Agents have no persistent memory.** After compaction, a correction you gave the agent is gone; the next session starts with the same defaults. Prompts fix instances, not patterns.
- **Linters are the most effective lever.** Strict types and linters convert behavioral rules into machine-enforceable constraints that survive context windows and model updates.
- **Common failure modes are predictable.** Overly defensive code, useless tests, and endpoints nobody asked for are recurring symptoms; knowing them in advance means the linter rule can be written before the first incident.
- **The advice comes from Sentry's production debugging agent.** Pstrucha works on the infrastructure behind Seer, Sentry's own coding agent, giving the argument direct production grounding rather than theoretical framing.

**[AI Writes More PRs. Who Validates Them? — Ali-Reza Adl-Tabatabai, Sonar](https://www.youtube.com/watch?v=uuwDWRbxoYo)**
AI coding tools increase both PR volume and PR size simultaneously, pushing teams toward a choice between slower CI or rubber-stamping — unless validation is automated at the same pace as generation.

- **More PRs plus bigger PRs multiplies review burden.** The compounding effect in both dimensions makes the validation problem qualitatively different from anything human-only teams dealt with before.
- **The answer is agentic validation in CI.** Adl-Tabatabai proposes an agent that reviews PRs with the same context the coding agent had when writing them, running in CI where quality gates already live.
- **Quality gates are already in the right place.** Extending CI with agentic review does not require new infrastructure — the leverage point is already there.
- **Background: Gitar, acquired by Sonar.** The work comes from a company built specifically around code verification, making agentic validation their core product thesis rather than a side feature.

**[Why 80% Reliability Isn't Good Enough — Felipe Blanes, Amazon AGI Lab](https://www.youtube.com/watch?v=Emo5FGGY-wM)**
Static benchmarks for browser agents look excellent until real customers use them in ways nobody anticipated — at that point, the gaps appear and there is nothing systematic in place to catch them.

- **The benchmark illusion is the central production risk.** A high benchmark score reflects the test distribution, not the distribution of real user behavior; these diverge the moment customers start using the product freely.
- **The fix is an eval flywheel built around real customer sessions.** Blanes's approach is to define evals from actual customer interactions rather than synthetic scenarios, so the benchmark tracks what customers actually do.
- **80% reliability fails in multi-step flows.** A 20% per-step failure rate compounds across a sequence of actions into much higher overall failure rates — the bar for browser agents is far above what typical benchmarks demand.
- **Lessons came from shipping Nova Act to GA.** Blanes worked directly with customers from research preview to general availability on AWS, so the failure modes he describes are production-observed, not lab-predicted.

**[How a Remote Company Builds AI Fluency — Em Shreve, Automattic](https://www.youtube.com/watch?v=3XI90A3ENSg)**
Automattic — 1,400+ people across 82 countries, fully remote — found that distributing AI tools does not change how people work; dedicating real structured time to learning does.

- **The bet is on time, not tool access.** Automattic runs two-week, in-person programs that combine workshops with real project work, rather than expecting fluency to emerge from access alone.
- **A remote-first company deliberately goes in-person for this.** The choice signals how seriously they treat the skills gap — it is a significant organizational investment, not a webinar.

- **1,400 people across 82 countries is a real-world adoption test.** The scale and distribution make Automattic's approach a meaningful experiment in org-wide AI fluency rather than a team-level pilot.

**[Brains vs Hands: How to Run AI Agents Safely in Production — Viren Baraiya](https://www.youtube.com/watch?v=NaOkR3VSfR4)**
The key to running agents safely in production is a clean architectural split: the model decides what should happen next, but it never controls how a production action is actually executed.

- **The brains-vs-hands split is the core safety principle.** The model is the reasoning layer; separate, controlled execution layers are the action layer — they operate only within pre-defined, auditable boundaries.
- **Real production agents are not chatbots.** They run on schedules, react to events, coordinate other agents, and can run for months; the harness around them starts to look like a distributed application.
- **The patterns come from workflow orchestration.** Baraiya, original creator of Netflix Conductor, draws a direct line from workflow orchestration to agent orchestration — the design lessons transfer.
- **Never let the model improvise production infrastructure changes.** The "hands" side should execute only pre-defined sequences; an agent ad-libbing how to restart a cluster is where production incidents start.

**[We Mapped 115 Microservices for Our Coding Agents — Kamalakannan Nandagopal, Postman](https://www.youtube.com/watch?v=k2ClBT4aqAg)**
Coding agents work well inside a single repo but break down across a real distributed system; Postman addressed this by building an API context graph that gives agents a structured map of all 115 microservices and thousands of endpoints.

- **Stale documentation is the root failure.** Skills and MCPs are only as useful as the context they carry; when documentation goes stale, agents make decisions on outdated information.
- **APIs are the right context layer for a distributed system.** Borrowing from how Postman's go-to-market team thinks about their product, the team realized their API graph was already the most current map of the system.
- **Agent memory is siloed per engineer.** Without a shared context layer, each engineer's agent has a different and incomplete view; the API context graph provides a single shared ground truth.
- **This is at production scale.** 115 microservices and thousands of endpoints is not a toy problem — Postman is applying this approach to their own live distributed system.

**[Turning Agent Memory Into Skills That Work — Will Lyon, Neo4j](https://www.youtube.com/watch?v=XPj3mIKEtI4)**
Embedding-based retrieval gives agents recall, but recall is not actionable knowledge; agents need memory that is connected, typed, and traceable to reason reliably across tasks.

- **Retrieval is not memory.** Vector search finds relevant content; it does not represent relationships, provenance, or how facts connect — which is what reasoning requires.
- **The context graph has three distinct layers.** Lyon describes short-term, long-term, and reasoning memory as separate layers with different storage and retrieval properties.
- **Entity extraction and resolution are foundational.** The same person, service, or concept must resolve to the same node across sessions before the graph becomes useful; this consistency work comes before any retrieval.
- **Decision traces enable multi-agent coordination.** Storing why the agent decided something — not just what it decided — lets other agents and humans audit and build on previous reasoning rather than starting blind.

**[Your AI Agent Has No Nervous System — Matt Gibiec, Dynatrace](https://www.youtube.com/watch?v=YNT7Plf9KIg)**
Coding agents operate fast but blind: without real observability into the environment they are changing, they guess at the state of running services, which leads to loops, operational issues, and security incidents.

- **Speed without environmental context is a liability.** Agents generate and apply changes quickly; without knowing how the system actually behaves, they cannot distinguish a safe change from a dangerous one.
- **The nervous system analogy is precise.** A nervous system provides real-time environmental feedback; Gibiec argues agents need the equivalent — live telemetry, not static documentation or a fixed tool list.
- **Three failure modes come from working blind.** Gibiec identifies loops (agent cannot tell if its change worked), operational issues (changes that degrade running services), and security issues (changes that create vulnerabilities).
- **Bluebox by Dynatrace is the proposed solution.** An observability agent that gives coding agents access to real runtime context, closing the loop between the code change and the system's actual response.

**[Why We Deleted Our MCP Server and Rebuilt It — Abhi Arya, Reducto](https://www.youtube.com/watch?v=jJQoVkd5yLg)**
Building agent-first software requires answering one question before anything else: who pays when the agent is wrong? Reducto learned this by shipping an MCP server with one tool per API endpoint that broke the same day the whole team used it.

- **One tool per endpoint is a trap.** The first MCP server demoed well but broke in practice because agents faced too many choices with too little context about which tool was right for which situation.
- **Three design approaches exist, with different accountability assumptions.** Arya identifies auto mode, user-first, and agent experience in service of the user as distinct models, each with a different answer to who absorbs the cost of an agent mistake.
- **Accountability drives the right design choice.** Whether the vendor, the user, or the team absorbs the failure cost determines which of the three approaches is correct — this is not a UX preference, it is a product contract.
- **Real team usage surfaces what demos hide.** The first server failed because demos are controlled and team-wide usage is not; the combinatorial confusion that breaks agents in practice is invisible in a prepared demo.
